1. Why a single tree isn't robust

A single decision tree has a serious weakness: it can be highly sensitive to small changes in the training data. In the cat classification example, changing just one of the 10 training examples (a single cat's features) is enough to flip which feature gives the highest information gain at the root — from ear shape to whiskers. That one swap cascades: the entire left and right subtrees built recursively from that root end up completely different.

Why this matters: a model whose output can flip dramatically because of one different training example isn't trustworthy — it suggests the tree is latching onto something fragile in this particular dataset rather than a genuinely stable pattern. The fix isn't to make one tree "more careful" — it's to stop relying on any single tree's decision at all.

2. Tree ensembles: voting instead of one answer

The fix is to build many decision trees — a tree ensemble — and let them vote. Given a new test example, you run it through every tree in the ensemble and take the majority vote of their predictions as the final answer.

Three trees in an ensemble, each trained slightly differently, voting on the same new test example. Majority vote here: 2 "Cat" vs. 1 "Not cat" → final prediction is Cat.

Why this matters: voting is precisely what neutralizes the fragility from Section 1. Any single tree still has the same sensitivity to small data changes as before — but now it only contributes one vote out of many. If one tree flips its answer due to some quirk, the majority of the other trees can still carry the correct prediction through. This directly makes the overall algorithm more robust.
The obvious question this raises: if you train the exact same algorithm on the exact same 10 examples multiple times, you'd just get the exact same tree every time — that gives you no diversity to vote across. You need a way to generate meaningfully different but still reasonable training sets from your one original dataset. That's exactly what Section 3 (sampling with replacement) solves.

3. Sampling with replacement

The lecture's own demonstration: imagine four colored tokens — red, yellow, green, blue — in a bag. To sample with replacement, you reach in, draw one token (say, green), put it back in the bag, shake, and draw again. Because the token goes back in before the next draw, you might draw the same color twice (e.g. green, yellow, blue, blue) and might not draw some color at all (no red, in that example).

Analogy: this is exactly like rolling a die repeatedly rather than dealing cards from a shrinking deck. Each "draw" doesn't reduce what's available for the next draw — every draw is independent and drawn from the full original set again.

Applied to building a tree ensemble: take your original m training examples (10 cats/dogs), and generate a new training set of the same size m by drawing examples one at a time with replacement from the original set. The resulting new training set will:

  • be the same size as the original (10 examples),
  • contain some repeated examples (since a given original example can be drawn more than once), and
  • not contain all of the original examples (since some may never get drawn at all).
Why this matters: this construction is exactly what solves the "meaningfully different but still reasonable" problem flagged in Section 2. Each newly-sampled training set is drawn from the same underlying distribution as the original (so a tree trained on it is still a plausible model of the same problem), but it isn't identical to the original (so different trees end up seeing slightly different data, and therefore end up making slightly different splits). That's the building block the random forest algorithm (Section 4) uses directly.

4. The random forest algorithm

Putting sampling with replacement to work, here's the base ensemble-building procedure, given a training set of size m:

For b = 1 to B:
  Use sampling with replacement to create a new training set of size m
  Train a decision tree on this new dataset

You repeat this B times, ending up with B different decision trees. A typical choice for B is around 64–128 (roughly 100). Setting B larger never hurts accuracy, but returns diminish quickly past ~100 — going to, say, 1000 trees mostly just slows down computation without meaningfully improving predictions.

This base procedure — repeatedly sampling with replacement and training a tree each time — is sometimes called a bagged decision tree (the name comes from that "put it in a bag" sampling procedure; conventionally written with a lowercase b for the loop counter and uppercase B for the total count, both standing for "bag").

Note: bagging alone already helps, but there's one more refinement that turns "bagged decision trees" specifically into the random forest algorithm — covered next.

5. Randomizing the feature choice

A remaining weakness with plain bagging: even though each tree trains on a slightly different sampled dataset, it's common for many or even all of the B trees to independently land on the same feature at the root node (and near the root), especially when one feature is a genuinely strong predictor. If all your trees agree at the top, they're not really diverse — and their votes become correlated rather than independent, undermining the whole point of ensembling.

The random forest's fix: at every node, when choosing which feature to split on, if n total features are available, restrict the algorithm to a random subset of k < n features, and let it pick the best (highest information gain) feature only from within that subset — not from all n.

Typical choice: k = √n

For example, with n = 3 features (ear shape, face shape, whiskers), this technique doesn't have much room to matter — it's really intended for problems where n is large (tens, hundreds of features), where forcing each split to consider only a random handful of them meaningfully diversifies which feature wins at any given node across different trees.

Why this matters: randomizing the feature subset at each split forces different trees to explore different "views" of the data, even when trained on similar sampled sets. Combined with sampling with replacement, the random forest algorithm ends up averaging over two independent sources of randomness (which examples, and which features are even considered) — and that's what makes it substantially more robust to small changes in the training set than either a single tree or plain bagging alone. Any one small change to the data has already been "explored" as one of many small variations the ensemble has seen, so it's much less likely to swing the overall (voted) output.

6. XGBoost: boosting and deliberate practice

Random forest builds all B trees independently and somewhat in parallel — each tree doesn't know or care what the others got right or wrong. Boosting changes that: trees are built one after another, and each new tree is deliberately steered toward the examples the ensemble-so-far is still getting wrong.

Analogy — deliberate practice: the lecture draws this directly from music practice. If you're learning a 5-minute piano piece, replaying the whole piece start to finish, over and over, is inefficient. It's far more effective to play through once, identify the specific passages you're still fumbling, and then drill just those passages repeatedly. Boosting applies the same idea to building trees: rather than treating every training example equally on every round, it identifies which examples the model built so far handles badly, and focuses the next tree's training more heavily on exactly those.

How the "reweighting" actually works, step by step

The boosting procedure modifies the sampling-with-replacement loop from Section 4 as follows:

For b = 1 to B:
  Use sampling with replacement to create a new training set of size m
  But instead of picking from all m examples with equal (1/m) probability, make it more likely to pick misclassified examples from previously trained trees
  Train a decision tree on this new dataset
  1. First tree (b = 1): built the ordinary way — sampling with replacement, every one of the m original examples equally likely to be picked (probability 1/m each).
  2. Evaluate: take the tree(s) built so far and run them (as an ensemble, if b > 1) against the original training set (not a resampled one). Mark each example as correctly or incorrectly classified.
  3. Second tree onward (b = 2, 3, ..., B): when sampling with replacement to build the next training set, the examples that are still being misclassified by trees 1 through b−1 are given a higher probability of being picked than the examples already being handled correctly. So the new sampled training set is skewed to contain more copies of the "hard" examples.
  4. A new tree is trained on this reweighted-and-resampled set — meaning it disproportionately sees the examples the ensemble is currently failing on, and is therefore pushed to learn splits that help specifically with those.
Why this matters — this is the part you specifically flagged: the reweighting is what turns "just building more trees" into "building trees that each patch a specific weakness of the ensemble so far." A plain bagged ensemble or random forest builds each tree blind to what the others got wrong; a boosted ensemble builds each new tree with its attention directed at the current failure cases, which is why boosting tends to converge to a stronger ensemble with fewer trees than un-directed bagging. The lecture is explicit that the precise mathematical rule for exactly how much more likely a misclassified example becomes is fairly complex — but you do not need those details to use a boosted-tree implementation effectively.
Note — how XGBoost specifically implements this: rather than literally re-running the sampling-with-replacement procedure with adjusted probabilities each round, XGBoost instead assigns different weights directly to different training examples (larger weight = more influence during that round's tree training on examples still being missed). This achieves the same "focus on what's still wrong" effect described above, without needing to actually generate a large number of randomly resampled datasets — which is part of why XGBoost is fast. The underlying intuition — deliberately practicing the hard parts — is unchanged; only the mechanism for expressing "pay more attention to this example" differs (a weight, rather than a resampling probability).

XGBoost in practice

XGBoost stands for eXtreme Gradient Boosting. It is by far the most commonly used decision-tree-ensemble implementation today — fast, open-source, and a frequent winner in both machine learning competitions (e.g. Kaggle) and commercial applications (XGBoost and deep learning are cited as the two algorithm families that dominate competition wins). Beyond the boosting mechanism itself, XGBoost also ships with good default choices for splitting criteria and stopping criteria, and has built-in regularization to help control overfitting.

Usage is nearly identical for classification and regression — only the class name changes:

Classification                          Regression
from xgboost import XGBClassifier       from xgboost import XGBRegressor

model = XGBClassifier()                 model = XGBRegressor()
model.fit(X_train, y_train)             model.fit(X_train, y_train)
y_pred = model.predict(X_test)          y_pred = model.predict(X_test)

7. Decision trees vs. neural networks

Both families are powerful, but they suit different situations. This isn't a "which is objectively better" comparison — it's about matching the tool to the data and constraints you have.

Decision Trees / Tree EnsemblesNeural Networks
Best data type Tabular / structured data — data that looks like a spreadsheet (rows = examples, columns = features, whether categorical or continuous) Works well on all data types: tabular, and also unstructured data (images, video, audio, text), and mixes of both
Unstructured data (images/audio/text) Not recommended Preferred choice
Training speed Fast Can be slower, especially large networks
Interpretability A single small tree (a few dozen nodes) can be printed and read by a human — though this is somewhat overstated once you have an ensemble of 100 large trees, which becomes just as hard to inspect directly and may need separate visualization tooling Generally treated as a "black box"
Transfer learning Not applicable / not typically used Works — critical when you only have a small dataset for your specific task, since you can pretrain on a much larger related dataset first
Stringing multiple models together Harder — you can only train one decision tree at a time Easier — multiple networks chained together can still all be trained jointly via gradient descent
Why this matters: this is a practical decision-making guide, not a theoretical ranking. If your data is genuinely tabular (the heart-disease dataset in this week's lab is a good example — patient age, blood pressure, cholesterol, categorical symptoms, etc.), trees and neural networks are often competitive with each other, and trees have the edge in training speed. The moment your data includes images, audio, or raw text, neural networks become the clear preferred choice, because trees have no natural way to exploit that kind of structure.
Practical recommendation from the lecture: if you've decided a tree-based approach fits your problem, use a tree ensemble rather than a single tree in almost all cases — and specifically, default to XGBoost for most applications. A single tree is only preferable under a genuinely tight computational budget, since an ensemble is inherently more expensive to train and run than one tree.

Both decision trees and neural networks fit into the same overall iterative development loop covered in Week 3 — choose architecture (model, data, etc.) → train model → run diagnostics (bias, variance, error analysis) → adjust → repeat. Because tree-based models train fast, that loop can typically be cycled through more quickly when using trees, which is itself a practical advantage during model development, independent of final accuracy.

8. Practice lab: implementing all three in scikit-learn

The lab uses a real tabular dataset — the Heart Failure Prediction dataset (11 patient features such as age, sex, chest pain type, resting blood pressure, cholesterol, and others, predicting a binary HeartDisease label) — and walks through building a DecisionTreeClassifier, a RandomForestClassifier, and an XGBClassifier, all from scikit-learn/XGBoost, on the same data.

Step 1 — One-hot encoding with pandas

Five of the eleven features are categorical with more than two possible values (Sex, ChestPainType, RestingECG, ExerciseAngina, ST_Slope), so they need one-hot encoding before any of these models can use them (matching Section 6 of Part 1). Rather than hand-building the binary columns, pandas' built-in pd.get_dummies does it directly:

cat_variables = ['Sex', 'ChestPainType', 'RestingECG',
                 'ExerciseAngina', 'ST_Slope']

# Replaces each categorical column with its one-hot encoded columns;
# non-categorical columns are left untouched.
df = pd.get_dummies(data = df,
                     prefix = cat_variables,
                     columns = cat_variables)
Note: binary features (already 0/1, or already only two categories) don't need one-hot encoding — encoding them would just recreate the same information in a different shape. The lab only applies get_dummies to the variables that have 3 or more distinct values, consistent with the "k possible values → k binary features" rule from Part 1, Section 6.

Step 2 — Splitting the dataset

X_train, X_val, y_train, y_val = train_test_split(
    df[features], df['HeartDisease'],
    train_size = 0.8, random_state = RANDOM_STATE)

An 80/20 train/validation split, with random_state fixed for reproducibility (this is the RANDOM_STATE = 55 passed to every sklearn call in the notebook).

Step 3 — Decision tree, and tuning against overfitting

Two hyperparameters are swept one at a time to see their effect on train vs. validation accuracy:

  • min_samples_split — the minimum number of examples required at a node before it's allowed to split further. Higher values reduce the number of splits and help reduce overfitting.
  • max_depth — the maximum depth the tree is allowed to reach. Lower values also reduce splits and help reduce overfitting.
model = DecisionTreeClassifier(min_samples_split = min_samples_split,
                                random_state = RANDOM_STATE).fit(X_train, y_train)

The lab's finding: pushing max_depth too low (below ~3) causes underfitting — both train and validation accuracy drop, because the tree can't make enough splits to separate the classes. Pushing it too high (≥5 or so) causes overfitting — training accuracy climbs while validation accuracy falls. The chosen sweet spot in the lab: max_depth = 4, min_samples_split = 50.

Why this matters: this is a direct, hands-on instance of the bias/variance tradeoff from Week 3 — too shallow a tree underfits (high bias), too deep a tree overfits (high variance) — with max_depth and min_samples_split acting as the tuning knobs that trade one against the other.

Step 4 — Random forest

Same hyperparameters apply (since a random forest is just an ensemble of decision trees), plus one new one: n_estimators — the number of trees in the forest (B from Section 4).

random_forest_model = RandomForestClassifier(n_estimators = 100,
                                              max_depth = 16,
                                              min_samples_split = 10).fit(X_train, y_train)

Two implementation notes worth keeping in mind:

  • max_features controls the k-out-of-n randomized feature subset from Section 5 (default behavior already implements the k = √n idea).
  • n_jobs lets multiple trees be trained in parallel across CPU cores, since fitting each tree is independent of the others — this only affects training speed, not the final result.

Step 5 — XGBoost, with early stopping

XGBoost adds one more important parameter beyond what a plain tree/forest has: the learning rate — the step size used internally by the gradient descent XGBoost runs to minimize error at each boosting round.

A distinctive and very practical XGBoost feature: it can take a separate evaluation set during .fit() and stop training automatically once further rounds stop helping:

n = int(len(X_train) * 0.8)  # 80% to actually fit, 20% held out to monitor
X_train_fit, X_train_eval, y_train_fit, y_train_eval = (
    X_train[:n], X_train[n:], y_train[:n], y_train[n:])

xgb_model = XGBClassifier(n_estimators = 500, learning_rate = 0.1,
                           verbosity = 1, random_state = RANDOM_STATE)
xgb_model.fit(X_train_fit, y_train_fit,
              eval_set = [(X_train_eval, y_train_eval)],
              early_stopping_rounds = 10)
How early_stopping_rounds actually behaves: even though n_estimators = 500 allows up to 500 trees, the model tracks whichever round so far had the best (lowest) evaluation metric. If 10 consecutive rounds pass without beating that best score, training stops early. In the lab's run, the best round was round 16, and training stopped at round 26 (16 + 10) — meaning only 26 trees were actually built, not 500. Important detail: the model returned is the one from the stopping round (26), not the best round (16) — so early_stopping_rounds is a stopping condition, not an automatic "roll back to the best checkpoint" mechanism.
Why this matters: more boosting rounds means more estimators, and more estimators can eventually mean overfitting — this is boosting's own version of the same overfitting risk that max_depth and min_samples_split manage for a single tree. Early stopping is a practical, largely automatic way to cap the number of rounds right around where validation performance stops improving, without you having to hand-tune n_estimators by trial and error.

Comparing all three

All three models expose the same basic interface (.fit(X_train, y_train), .predict(X)), so comparing them is just a matter of computing accuracy_score on train and validation sets for each. In the lab's run, the tuned decision tree, tuned random forest, and XGBoost end up in a similar ballpark on validation accuracy for this dataset — consistent with Section 7's point that trees and neural networks (and, by extension, different tree-ensemble variants) are often competitive with each other on genuinely tabular data.

9. Summary

ConceptRole
Tree ensembleMultiple trees voting together — fixes a single tree's sensitivity to small data changes
Sampling with replacementDraws a new same-size training set from the original, with repeats possible — the mechanism that makes each tree in the ensemble see slightly different data
Random forestBagging (sampling w/ replacement + train a tree, repeated B times) plus randomizing which k of n features each split is even allowed to consider
k = √nTypical size of the randomly-chosen feature subset at each split in a random forest
Boosting / XGBoostTrees built sequentially, each one focused (via resampling probability, or in XGBoost's case, example weights) on the examples the ensemble-so-far is still misclassifying
Decision trees vs. neural networksTrees: fast, good for tabular data, ensembles recommended (XGBoost by default). Neural nets: needed for unstructured data, support transfer learning and joint training of chained models
Lab hyperparametersmax_depth / min_samples_split control over/underfitting for a single tree; n_estimators adds tree count for forests; learning_rate + early_stopping_rounds are XGBoost-specific controls
Don't conflate bagging and boosting: both build many trees, but bagging (plain random forest) builds them independently and in parallel, each blind to the others' mistakes — diversity comes purely from random sampling of data and features. Boosting (XGBoost) builds them sequentially, and each new tree is deliberately pointed at the current ensemble's weak spots. This is the single most important distinction between the two families covered this week.
