1. Why "just try things" isn't good enough

Say you've implemented regularized linear regression for housing prices:

J(w,b) = (1/2m) ∑ (fw,b(x(i)) − y(i))2  +  (λ/2m) ∑ wj2

It makes unacceptably large errors on new predictions. There's a long list of things you could try next: get more training examples, use a smaller set of features, add more features, add polynomial features, decrease λ, or increase λ.

Every one of these is plausible. The problem is that on any given project, some of these will help a lot and others will do almost nothing — and you can't tell which just by staring at the list. Teams that guess blindly can burn months collecting more data only to find that data was never the bottleneck.

Why this matters: the whole point of this week is to replace guessing with diagnostics — tests you run that tell you which of these options is actually worth your time, before you spend weeks on it. A diagnostic can take real effort to set up, but a good one can save you months by ruling out the wrong fix early. Before you can run any diagnostic, though, you need a systematic, numeric way to say "how well is this model actually doing?" — that's the whole point of Sections 2–3.

2. Evaluating a model systematically: J_train and J_test

With one input feature, you could just plot f(x) and eyeball whether the curve looks reasonable. A 4th-order polynomial fit to 5 points might hug the training data perfectly while being obviously too wiggly to trust on new houses.

But once you have more than 1–2 features (size, bedrooms, floors, age, ...), you can't plot a 4-dimensional function to "look" at it. You need a number, not a picture.

The fix: split off a test set

Instead of using 100% of your data to fit w and b, split it — commonly 70/30 or 80/20:

  • Training set (x(1),y(1)) ... (x(m_train),y(m_train)) — used to fit the parameters
  • Test set (xtest(1),ytest(1)) ... (xtest(m_test),ytest(m_test)) — held out, never used to fit parameters

Fit w, b by minimizing J(w,b) on the training portion only (this still includes the regularization term). Then compute two separate quantities, neither of which includes the regularization term — regularization is a training-time tool, not part of how you measure performance:

Jtrain(w,b) = (1/2mtrain) ∑i=1m_train (fw,b(xtrain(i)) − ytrain(i))2

Jtest(w,b) = (1/2mtest) ∑i=1m_test (fw,b(xtest(i)) − ytest(i))2

For the overfit 4th-order polynomial: Jtrain will be near zero (it memorized those 5 points), but Jtest, computed on houses the model never saw, will be large. That gap between a low Jtrain and a high Jtest is the numeric signature of overfitting — and it's the thing you can compute even when you have 100 features and can't plot anything.

Why this matters: Jtrain tells you how well the model fits data it has already seen — which is almost always optimistic, since the parameters were chosen specifically to make Jtrain small. Jtest is your proxy for generalization error: how well the model will do on brand-new houses nobody has shown it yet. That's the number you actually care about in production.

3. The same idea for classification

For classification (e.g. handwritten digit 0 vs 1), fit w, b by minimizing the regularized logistic cost, then define Jtrain and Jtest the same way but using the logistic loss instead of squared error:

Jtest(w,b) = −(1/mtest) ∑i=1m_test [ ytest(i) log(f(xtest(i))) + (1−ytest(i)) log(1−f(xtest(i))) ]

In practice, though, there's a version that's used even more often for classification: instead of averaging the logistic loss, just look at the fraction of examples the model got wrong.

ŷ = 1 if fw,b(x(i)) ≥ 0.5, else 0

Jtest(w,b) = fraction of the test set where ŷ ≠ y     Jtrain(w,b) = fraction of the training set where ŷ ≠ y
Note: this misclassification-rate version is more interpretable ("12% of test examples wrong") and is what's used later this week when talking about bias/variance for classifiers, but the loss-based version is mathematically valid too — they're two ways of asking the same question, "how wrong is this model on data it hasn't seen?"

4. The hidden flaw: using the test set to choose a model

Now suppose you don't just want to fit one model — you want to decide which model to use. Try degree d = 1, 2, 3, ... up to 10, fit each on the training set, and get w<1>,b<1> through w<10>,b<10>.

The tempting procedure: compute Jtest for every one of the 10 fitted models, pick whichever degree gives the lowest Jtest (say d = 5), and then report that same Jtest(w<5>,b<5>) as your estimate of how well the model generalizes.

Why this is flawed: the degree d is itself a parameter of your model — and you just chose it specifically because it minimized Jtest. That means Jtest was used in the decision process, exactly the same way the training set was used to fit w and b. So Jtest(w<5>,b<5>) is now an overly optimistic (too low) estimate of true generalization error — it's been "peeked at" during model selection, so it no longer tells you honestly how the model will do on data it's never influenced in any way.
Analogy: imagine grading 10 different exam versions against the answer key, then handing in whichever version scored highest as "proof" of how well you know the material. The score is real, but it's inflated — you didn't pick the version at random, you picked the one the answer key happened to like best. To get an honest score, you need a fresh, never-consulted exam.

This is exactly the same failure mode as fitting w, b on the training set and then reporting Jtrain as the generalization error — just one level higher up, at the level of choosing d instead of choosing w and b.

5. What cross validation actually is, and why it exists

The fix is simple in structure but important in effect: split the data into three parts instead of two.

  • Training set — mtrain examples, used to fit w and b for each candidate model.
  • Cross-validation set (also called the validation set or the dev set — all three names mean the same thing) — mcv examples, used only to compare candidate models and pick things like the polynomial degree or network architecture.
  • Test set — mtest examples, touched exactly once, at the very end, to report a final, honest generalization number.
Jcv(w,b) = (1/2mcv) ∑i=1m_cv (fw,b(xcv(i)) − ycv(i))2

This is the direct answer to "what is cross validation and why is it used": it's a second held-out set, separate from the test set, whose entire job is to absorb the "peeking" that happens during model selection. Once you've picked a degree by comparing Jcv across candidates, the test set still hasn't been looked at by anyone or anything — so Jtest on the final chosen model is a fair, unbiased estimate of generalization error.

Why this matters: without a CV set, the only held-out data you have is the test set — so the moment you use it to choose anything (a degree, a λ, a network size), you've contaminated it, and it can no longer honestly answer "how will this do on the real world?" Cross validation exists purely to give the model-selection step its own sandbox to play in, so the test set can stay clean for its one job: the final, one-time report card.
Analogy: think of it like a hiring process with a practice interview (training set), a set of finalist interviews used to decide who gets the job (cross-validation set), and a totally separate reference check done after the decision, just to confirm the hire was good (test set). If you used the same finalist interviews both to pick the winner and to prove they were the best candidate, of course they'd look great — you picked them precisely because they looked great on that exact interview.
Terminology: "cross-validation set," "validation set," and "dev set" (short for development set) are used interchangeably across courses and papers — they refer to the exact same held-out subset described here. The lecture notes the instructor personally prefers "dev set" for brevity, but "cross-validation" is the more common term you'll see used.

6. Model selection with train / CV / test

Putting it together, the corrected procedure for choosing a polynomial degree:

  1. For each candidate d = 1, 2, ..., 10: fit w<d>, b<d> using only the training set.
  2. Evaluate every candidate on the cross-validation set: compute Jcv(w<1>,b<1>) through Jcv(w<10>,b<10>).
  3. Pick the degree with the lowest Jcv — say d = 4.
  4. Only now, report Jtest(w<4>,b<4>) as the generalization-error estimate. The test set was never consulted while choosing d, w, or b, so this number is trustworthy.
Rule of thumb worth internalizing: make every decision about your model (parameters, degree, architecture, hyperparameters) using only the training set and the cross-validation set. Never look at the test set until you have one final model you're committing to. The moment the test set influences a decision, it stops being a fair test set.

7. Same idea for choosing a neural network architecture

This procedure isn't specific to polynomial degree — it generalizes to any "which model structure should I use?" question. For handwritten digit recognition, you might compare a small, medium, and large network:

CandidateSelected usingReported using
Small NN → w1,b1Jcv for each (fraction misclassified, since this is classification)Jtest — only for the one network with the lowest Jcv
Medium NN → w2,b2
Large NN → w3,b3

Train all three on the training set, compare them on Jcv, pick whichever architecture scores lowest there, and only then check Jtest on that one chosen network to report generalization performance. This is described in the lecture as a widely used, practical procedure — the standard way to answer "how many layers / units should I use?" without guessing.

8. Lab walkthrough: doing this in code

From C2_W3_Lab_01_Model_Evaluation_and_Selection.ipynb — the same three-way split and comparison, implemented with scikit-learn.

Splitting into train / CV / test (60/20/20)

from sklearn.model_selection import train_test_split

# Get 60% of the dataset as the training set. Put the remaining 40% into temporary variables.
x_train, x_, y_train, y_ = train_test_split(x, y, test_size=0.40, random_state=1)

# Split that 40% in half: one half becomes cross validation, the other becomes test
x_cv, x_test, y_cv, y_test = train_test_split(x_, y_, test_size=0.50, random_state=1)

del x_, y_
Note: train_test_split only splits data two ways at a time, so a 60/20/20 three-way split is done as two successive 2-way splits: 60/40 first, then the 40% half is split again 50/50 to land on 20/20.

Feature scaling — fit on train, only transform on CV/test

scaler_linear = StandardScaler()

# Compute mean/std from the TRAINING set, and scale the training set with it
X_train_scaled = scaler_linear.fit_transform(x_train)

# Reuse that SAME mean/std to scale the CV set — never re-fit on CV data
X_cv_scaled = scaler_linear.transform(x_cv)
Common mistake to avoid: always use .fit_transform() on the training set and only .transform() (never re-fit) on the CV and test sets. If you compute a fresh mean/std from the CV or test data, you've let information about that "unseen" data leak into your scaling — quietly breaking the whole point of holding it out.

Comparing 10 polynomial degrees via J_cv

train_mses, cv_mses, models, polys, scalers = [], [], [], [], []

for degree in range(1, 11):
    poly = PolynomialFeatures(degree, include_bias=False)
    X_train_mapped = poly.fit_transform(x_train)

    scaler_poly = StandardScaler()
    X_train_mapped_scaled = scaler_poly.fit_transform(X_train_mapped)

    model = LinearRegression()
    model.fit(X_train_mapped_scaled, y_train)

    # ... same poly + scaler are reused (via .transform only) on x_cv ...
    # ... train_mses / cv_mses collected each loop ...

# Pick the degree with the lowest CV error
degree = np.argmin(cv_mses) + 1
print(f"Lowest CV MSE is found in the model with degree={degree}")

Only after that degree is chosen does the lab touch the test set:

X_test_mapped = polys[degree-1].transform(x_test)
X_test_mapped_scaled = scalers[degree-1].transform(X_test_mapped)

yhat = models[degree-1].predict(X_test_mapped_scaled)
test_mse = mean_squared_error(y_test, yhat) / 2
Note: notice x_test never appears inside the for degree in range(1, 11) loop — it only shows up once, after degree has already been decided. That ordering in the code is the literal expression of the "don't let the test set influence decisions" rule from Section 6.

The same pattern for neural networks and for classification

The lab repeats the identical structure twice more: once comparing 3 candidate neural network architectures via Jcv (MSE) before checking one final Jtest, and once for a classification dataset (x1, x2 → 0/1) using a 60/20/20 split, where Jcv and Jtest become misclassification fractions instead of MSE — matching the classification formulas from Section 3.
