1. Finding unusual events: the density-estimation idea

Anomaly detection is your second unsupervised learning algorithm. Given an unlabeled dataset of mostly normal events, it learns what "normal" looks like, and then flags anything that deviates significantly from that as a possible anomaly.

The running example: an aircraft engine manufacturer measures features for every engine it produces — heat generated (x₁), vibration intensity (x₂), and so on. Most manufactured engines are fine; only a small number are flawed. The question for a brand-new engine is: does it look similar to the engines seen before, or does it look weird enough to warrant a closer inspection before it's shipped?

The standard approach is density estimation: build a model of p(x) — the probability of seeing a given combination of feature values — directly from the training data. Regions where training examples cluster densely get assigned high probability; regions far from any training data get assigned low probability. Given a new example x_test, you compute p(x_test), and:

if p(x_test) < ε  →  flag as anomaly
if p(x_test) ≥ ε  →  treat as normal

(ε, epsilon, is just a small threshold number you choose.)

Why this matters: notice this never requires labeled anomalous examples to build the core model — p(x) is learned purely from normal data. That's what makes this unsupervised, and it's also the source of one of anomaly detection's biggest practical strengths (covered in Section 6): the model doesn't need to have seen a specific type of failure before to flag it as unusual.

Real-world uses beyond aircraft engines: fraud detection (modeling p(x) over a user's login frequency, page visits, transaction count, typing speed, etc.), manufacturing QA for circuit boards/smartphones/etc., and monitoring machines in a data center or cell towers (memory use, CPU load, network traffic) to catch hardware failures or intrusions before they cause bigger problems.

2. The Gaussian (normal) distribution

To actually build p(x), we need a concrete mathematical model of "probability of a value" — that's the Gaussian distribution (also called the normal distribution, or the bell-shaped curve).

For a single number x, the Gaussian distribution is described by two parameters: the mean μ (where the curve is centered) and the variance σ² (how wide/spread out the curve is; σ itself is the standard deviation).

p(x; μ, σ²) = (1 / √(2πσ²)) · exp( −(x−μ)² / (2σ²) )

Changing μ shifts the curve left/right without changing its shape. Changing σ changes the width: a smaller σ gives a taller, narrower curve (values tightly clustered near μ); a larger σ gives a shorter, wider curve (values more spread out). The area under the curve always equals 1, which is why a narrower curve must also be taller.

Given a training set of plain numbers, you estimate μ and σ² directly from the data:

μ = (1/m) ∑i=1m x⁽ⁱ⁾      σ² = (1/m) ∑i=1m (x⁽ⁱ⁾ − μ)²

(These are just "the average" and "the average squared deviation from the average" — the same quantities you'd compute for any dataset. Note: some statistics courses divide by m−1 instead of m for the variance; in practice this makes almost no difference, and the lectures use 1/m throughout.)

Analogy: think of μ as "where most values tend to sit" and σ as "how much they typically wander from that." A tight cluster of test scores around 75 has small σ; scores scattered from 20 to 100 have large σ, even if both groups happen to average out to the same μ.

3. The anomaly detection algorithm

Real examples have n features, not just one — an engine might have heat, vibration, pressure, and more. The algorithm extends the single-number Gaussian idea by modeling each feature separately with its own Gaussian, then multiplying them together:

p(x) = p(x₁; μ₁, σ₁²) · p(x₂; μ₂, σ₂²) · ... · p(xₙ; μₙ, σₙ²) = ∏j=1n p(xⱼ; μⱼ, σⱼ²)

This multiplication assumes the features are statistically independent of each other — knowing the value of x₁ tells you nothing about x₂'s value. In practice, the algorithm still tends to work reasonably well even when this assumption is only approximately true; you don't need a deep grasp of statistical independence to use it effectively.

Why multiply, intuitively: suppose there's a 1-in-10 chance an engine runs unusually hot, and separately a 1-in-20 chance it vibrates unusually hard. The chance that a given engine does both is (1/10) × (1/20) = 1/200 — multiplying captures how much rarer it is for several unusual things to happen together than for any one of them alone.

The algorithm, step by step

  1. Choose n features x₁, ..., xₙ that you believe might be indicative of anomalies.
  2. Fit parameters: compute μⱼ and σⱼ² for every feature j, using the ordinary mean/variance formulas from Section 2, applied separately to each feature's column of data. (Vectorized: μ is just the average of all the training vectors x⁽ⁱ⁾ at once.)
  3. Given a new example x, compute p(x) using the product formula above, and flag it as an anomaly if p(x) < ε.
Why this matters — the real intuition behind the whole algorithm: because p(x) is a product of per-feature probabilities, the overall p(x) becomes very small if even just one feature has a value that's unusually large or unusually small compared to what the model has seen for that feature. In other words, the algorithm is really a systematic way of asking, feature by feature: "is any single one of these values weird on its own?" — and if so, flagging the whole example, even if every other feature looks perfectly ordinary.

4. Developing and evaluating an anomaly detection system

This is the part worth slowing down on, because it's where a lot of the practical difficulty in anomaly detection actually lives.

Why you need "real-number evaluation" at all

When you're tuning an anomaly detection system — trying different features, adjusting ε — every one of those decisions is much easier to make correctly if you have a single number that tells you whether the change made things better or worse. Without that, you're just guessing.

Where the labels come from

Anomaly detection is fundamentally unsupervised — you fit p(x) using only unlabeled data, treated as if it's all normal (y = 0). But in practice, you usually do have a small number of previously confirmed anomalies lying around (a handful of known-flawed engines, say). The trick is to reserve those labeled examples specifically for evaluation, not for fitting p(x) itself:

Training set: x⁽¹⁾, ..., x⁽ᵐ⁾  (assume ALL normal — y = 0 for every training example, even if a few anomalies accidentally slip in)

Cross-validation set: (x_cv⁽¹⁾, y_cv⁽¹⁾), ..., (x_cv⁽ᵐᶜᵛ⁾, y_cv⁽ᵐᶜᵛ⁾)  — mostly normal (y=0), plus a few known anomalies (y=1)
Test set: (x_test⁽¹⁾, y_test⁽¹⁾), ..., (x_test⁽ᵐᵗᵉˢᵗ⁾, y_test⁽ᵐᵗᵉˢᵗ⁾)  — same structure as the CV set

Worked example: 10,000 engines

Say you've manufactured 10,000 good engines and have 20 known-flawed ones on record. A typical split:

SetNormal (y=0)Anomalous (y=1)Purpose
Training6,0000 (assumed all normal)Fit the Gaussian parameters μ, σ²
Cross-validation2,00010Tune ε, tune which features xⱼ to use
Test2,00010Final, unbiased evaluation after tuning is done
Note: it's fine if a genuine anomaly accidentally ends up in the unlabeled training set — the algorithm will typically still do okay, since it's the overwhelming majority of normal examples that shapes the fitted Gaussian.

The "no test set" alternative

When you have very few labeled anomalies (say, only 2), splitting them further into both a CV set and a separate test set leaves you with almost nothing in either. In that case, a common alternative is to skip the test set entirely and put all your labeled anomalies into the cross-validation set alone (e.g., train on 6,000 good engines; CV on the remaining 4,000 good engines plus all 20 anomalies).

The trade-off with this alternative: you can still tune ε and your features using the CV set, but you lose any independent, unbiased way to measure how the final system will perform on genuinely new data — because every decision you made was tuned against the very same set you'd otherwise use to check yourself. This raises real risk of overfitting your choices (of ε, of which features to include) specifically to that CV set, so its reported performance may be optimistic compared to what you'll actually see later. Use this fallback only when you truly don't have enough labeled anomalies to do otherwise.

The actual evaluation procedure

  1. Fit p(x) on the training set only.
  2. For each cross-validation (or test) example x, predict: y = 1 if p(x) < ε, else y = 0.
  3. Compare these predictions against the true labels y_cv to see how well the algorithm is actually doing.
Why plain accuracy is the wrong metric here: in the worked example, the CV set has 2,000 normal examples and only 10 anomalies — a massively skewed (imbalanced) dataset. A do-nothing classifier that labels every single example "normal" would already score roughly 2000/2010 ≈ 99.5% accuracy while catching zero anomalies — which is exactly the failure mode that skewed-data metrics (Section 5) exist to catch. This is the direct continuation of the skewed-datasets discussion from Course 2, Week 3.

5. Quick recap: precision, recall, and F1 score

You've seen these before, but here's a self-contained recap so this file stands on its own.

Once you've labeled predictions as "anomaly" (1) or "normal" (0) and compared them to the true labels, every prediction falls into one of four buckets:

Actually anomalous (y=1)Actually normal (y=0)
Predicted anomalyTrue Positive (TP) — correctly caughtFalse Positive (FP) — false alarm
Predicted normalFalse Negative (FN) — missed anomalyTrue Negative (TN) — correctly cleared
Precision = TP / (TP + FP)      Recall = TP / (TP + FN)
  • Precision answers: "Of everything I flagged as an anomaly, what fraction actually was one?" Low precision means you're crying wolf a lot — flooding your security/inspection team with false alarms.
  • Recall answers: "Of all the anomalies that actually existed, what fraction did I actually catch?" Low recall means real problems are slipping through undetected.

These two pull against each other: an extremely cautious threshold (very small ε, flags almost nothing) tends to have high precision but low recall (you rarely cry wolf, but you also miss most real anomalies). A very sensitive threshold (large ε, flags almost everything) does the opposite. Neither number alone tells the full story, which is why the F1 score combines them into one number via the harmonic mean:

F1 = 2 · (Precision · Recall) / (Precision + Recall)
Why the harmonic mean and not a plain average: the harmonic mean punishes a big imbalance between the two numbers much more than an ordinary average would. A model with precision = 1.0 and recall = 0.01 has a plain average of about 0.5 (looks decent) but an F1 of about 0.02 (correctly reveals it's nearly useless) — because it's barely catching any real anomalies at all. F1 forces both precision and recall to actually be reasonably good before it gives you a high score.
How this applies here, specifically: because the CV/test sets have very few positive (anomalous) examples, precision/recall/F1 — rather than plain accuracy — are what you'd actually compute to decide whether one choice of ε or one choice of features is better than another. Whichever choice gives the higher F1 (or whichever balance of precision/recall matters more for your application — e.g., in aircraft engines you'd likely prioritize recall, since missing a real defect is far costlier than an extra inspection) is the one you keep.

6. Anomaly detection vs. supervised learning

If you already have some labeled anomalies for evaluation, a natural question is: why not just use those labels to train a supervised classifier instead? The choice is genuinely subtle, and comes down to two related factors.

Anomaly detectionSupervised learning
Typical data shape Very few positive (y=1) examples — 0 to 20 is common — and a large number of negative examples A reasonably large number of both positive and negative examples
Core assumption Future anomalies may look nothing like any positive example seen so far — there could be many different, unrelated "types" of anomaly Future positive examples are likely to resemble the positive examples already in the training set
What's actually learned What normal (y=0) data looks like — anything that deviates a lot gets flagged, including entirely new failure modes never seen before A boundary that separates the specific known positive class from the negative class
Why this matters — the core distinction, restated simply: anomaly detection asks "does this look like the normal stuff I've seen?" and flags anything that doesn't — so a brand-new kind of failure, never observed before, still gets caught, because it just won't resemble the normal data either. Supervised learning instead asks "does this look like the specific bad examples I was shown?" — so it's well-suited to a problem where the bad cases you'll see in the future look basically like the bad cases you've already collected, but poorly suited to catching a genuinely novel kind of failure your training set never contained.

The examples that make this concrete

ApplicationBest fitWhy
Financial fraudAnomaly detectionNew fraud schemes appear constantly; a scheme invented next year may look nothing like anything in your training data
Email spamSupervised learningSpam keeps promoting similar categories of things (pills, cheap watches, etc.) year after year — future spam resembles past spam closely enough
Manufacturing — brand-new, never-seen defect typeAnomaly detectionYou want to catch failure modes you've never encountered, e.g. a new way an aircraft engine could break
Manufacturing — known recurring defect (e.g. scratched phone screens)Supervised learningYou already have plenty of labeled examples of this exact, recurring defect type
Data-center machines / security intrusionsAnomaly detectionA hacked machine, or a new hacking technique, can behave in a way nothing in the training set resembles
Weather prediction, disease classification from known symptomsSupervised learningA small number of well-understood output categories recur consistently over time

For additional external framing on this same supervised-vs-unsupervised distinction as applied to anomaly detection specifically, GeeksforGeeks' "Machine Learning for Anomaly Detection" article covers the same split (supervised anomaly detection needing a labeled dataset of both normal and anomalous samples, vs. unsupervised methods that only assume anomalies are rare and statistically different from normal data) from an implementation-focused angle, which can be a useful second pass if this section still feels abstract.

One more nuance worth keeping in mind: even with only ~20 labeled positive examples, it might technically be possible to train a supervised model — the deciding factor isn't strictly the count, it's whether you believe future anomalies will resemble your current handful of examples (→ supervised) or could be something entirely new (→ anomaly detection).

7. Choosing what features to use

Feature choice matters more for anomaly detection than for supervised learning. In supervised learning, mislabeled or irrelevant features are less damaging because the labels y give the algorithm a strong enough signal to learn what to ignore or how to re-weight things. Anomaly detection has no such signal — it only sees unlabeled data — so it's much harder for the algorithm to "figure out on its own" that a feature is unhelpful. That makes careful, manual feature curation a bigger part of the job here.

Step 1 — try to make features look more Gaussian

Since the whole algorithm models each feature as Gaussian, features that are already roughly bell-shaped tend to work best. The practical workflow: plot a histogram of the feature (plt.hist(x)). If it already looks symmetric and bell-shaped, keep it as-is. If it's skewed (e.g., piles up near zero and tails off to the right), try transforming it and re-plotting until it looks more Gaussian:

x ← log(x)    or    x ← log(x + c)    or    x ← √x    or    x ← x^(1/3)    (or other fractional powers)

In practice this is trial and error in a notebook: try np.log(x), look at the histogram, try a different exponent or a different constant c, and keep whichever transform looks most symmetric/bell-shaped. (A larger value of c transforms the distribution less strongly — it's a tunable knob, not a fixed constant.) There exist formal statistical tests for "how Gaussian is this," but in practice, eyeballing a histogram and picking something reasonable works fine for this purpose.

Practical gotcha: log(0) is undefined (negative infinity), so if your feature contains zeros, you'll hit an error taking a raw log — this is exactly why log(x + c) with a small constant c (e.g. 0.001) is used instead of plain log(x).
Don't forget: whatever transformation you apply to a feature in the training set, you must apply the exact same transformation to that feature in the cross-validation and test sets too — otherwise you're comparing p(x) computed on inconsistent scales.

Step 2 — engineer features that specifically separate anomalies from normal data

Beyond just "make it Gaussian," you want features that will genuinely take on unusual values specifically when something is wrong. Concretely, when choosing features to monitor computers in a data center, you might start with:

x₁ = memory use    x₂ = disk accesses/sec    x₃ = CPU load    x₄ = network traffic

But a machine could have high CPU load and high network traffic totally normally (e.g. it's serving lots of video). What's actually unusual is a machine with high CPU load and unusually low network traffic — that combination, on its own, isn't captured well by any single one of x₁–x₄ in isolation. So you engineer a new, combined feature:

x₅ = CPU load / network traffic      x₆ = (CPU load)² / network traffic
Why this matters: this is the same underlying principle as Section 3's "one weird feature tanks the whole product" — but applied in reverse, as a design tool. If no single existing feature is unusual on its own for a given anomaly, but a specific ratio or combination of features is, then engineering that combination directly into a new feature gives the Gaussian model something concrete to catch. The goal for any candidate feature is: it should be large (typical) for normal examples, and become noticeably small (atypical) specifically for the anomalies you care about in your cross-validation set.

8. Error analysis and improving the feature set

After training, the goal is: p(x) should be ≥ ε (large) for normal examples, and < ε (small) specifically for anomalous ones. The most common problem you'll actually run into: p(x) ends up comparable — and large — for both normal and anomalous examples, meaning the model can't tell them apart with your current feature set and threshold.

Concretely: imagine plotting a single feature x₁ (say, number of transactions) for a fraud-detection problem. Most points cluster together, and there's one anomalous point sitting just slightly past the edge of that main cluster. Because it's only slightly outside the bulk of normal data, the fitted Gaussian may still assign it a fairly high p(x) — not low enough to fall below ε. The algorithm fails to flag it, even though a human looking at the full picture might recognize something is off.

The fix: look at specific missed anomalies, and ask what a human would have used to catch them

This is a manual, inspection-driven process, structurally similar to error analysis in supervised learning:

  1. Train the model, then look specifically at which anomalies in the cross-validation set the algorithm is failing to flag (p(x) came out too large for them).
  2. For each missed case, ask: "what made me (a human) suspect this was anomalous, even though this feature's value looked ordinary?"
  3. If you can identify a new feature that captures that intuition, add it.

Worked example: suppose a fraudulent user's number of transactions (x₁) looks completely normal — nothing suspicious there. But you notice this same user has an unusually fast typing speed — a totally different signal x₂ that the model wasn't using at all. Adding x₂ = typing speed as a second feature means the anomaly detector now fits a 2D Gaussian using both x₁ and x₂ together. Even though this user's x₁ was unremarkable, their combination of (ordinary x₁, extreme x₂) now sits clearly outside the high-probability region of the fitted 2D Gaussian — and gets correctly flagged.

Why this matters: this shows precisely why "p(x) is comparable for normal and anomalous examples" is usually a feature problem, not necessarily a fundamentally broken model. The Gaussian machinery itself doesn't change — what changes is giving it a dimension along which the anomaly actually stands out. This is also why Section 7's advice to engineer combined/ratio features (like CPU-load-over-network-traffic) is so directly useful here: those engineered features are often exactly the kind of new signal that turns an undetectable anomaly into a detectable one.
The full development loop, tied together: train p(x) on the training set → evaluate on the CV set using precision/recall/F1 (Sections 4–5) → for anomalies still being missed, do this error-analysis inspection → engineer or transform features (Section 7) based on what you find → re-fit and re-evaluate. This loop is the practical core of building a working anomaly detection system — it's rarely a one-shot fit.
