1. Discrete vs. continuous state spaces

Every example used so far (the Mars rover) had a discrete state space — the rover could only be in one of exactly 6 positions, numbered 1 through 6. Most real robots aren't confined to a small numbered set of positions; they can occupy any of an unlimited range of positions along a continuum. That's a continuous state space.

Discrete: a small fixed set of labeled positions. Continuous: any real number within a valid range.

Why this distinction matters: everything covered so far — Q(s,a) tables, the Bellman equation written out state by state, the little 6-row diagrams — implicitly assumed you could list every state and store a number for each one. That approach breaks down completely once a state is a continuous vector: there are infinitely many possible states, so you cannot build a table with one row per state. This is precisely the gap that motivates using a neural network to approximate Q(s,a) instead of a table (Section 5 onward) — a function approximator can generalize across states it has never exactly seen before, which a lookup table cannot.

2. Continuous-state examples: truck and helicopter

Two examples illustrate how a continuous state is represented as a vector of numbers, rather than a single discrete label:

Self-driving car / truck

s = [ x, y, θ, ẋ, ẏ, θ̇ ]
SymbolMeaning
x, yposition on the ground plane
θ (theta)orientation — which way the truck is facing (0–360°)
ẋ, ẏvelocity in the x and y directions (the dot notation means "rate of change")
θ̇ (theta-dot)how quickly the orientation is changing — the turning rate

Autonomous helicopter

s = [ x, y, z, φ, θ, ω, ẋ, ẏ, ż, φ̇, θ̇, ω̇ ]   (12 numbers)
SymbolMeaning
x, y, zposition — north-south, east-west, and height above ground
φ (roll)tilting left/right
θ (pitch)tilting forward/backward
ω (yaw)compass heading — north, east, south, west
ẋ, ẏ, żvelocity in each direction
φ̇, θ̇, ω̇angular velocity — how fast roll, pitch, and yaw are each changing
Why list all 12 numbers instead of a simpler summary: the policy needs enough information to make a genuinely good control decision, and a helicopter's behavior depends on both where it is and how it's currently moving/rotating. Position alone doesn't tell you whether the helicopter is about to tip over — the roll angle and its rate of change do. This full 12-number vector is fed as input to the policy on every decision.

Why l and r are included as their own binary variables: the lecture explains this is because a small difference in exact positioning matters a lot for whether the lander has actually landed — a leg touching the ground vs. not touching it is close to a discrete, binary fact, even though the rest of the state is continuous. Rather than trying to infer "has it landed" purely from y and ẏ, the state vector just includes that fact directly.

Why the reward function is this elaborate: the lecture is explicit that this is a "moderately complex" reward function, deliberately shaped by its designers to encourage exactly the behaviors wanted (landing gently, in the right spot, without wasting fuel) and discourage the ones that aren't (crashing, drifting away, firing thrusters needlessly). This is offered as a general lesson for anyone building their own RL application: it usually takes real thought to translate "what I want" into a reward function, but that translation is still typically far easier than trying to hand-specify the exact correct action for every possible state directly.

4. The lunar lander as an MDP

Learn a policy π that, given state s, picks action a = π(s) so as to maximize the return, using γ = 0.985.
Why γ = 0.985, close to 1: this echoes the pattern from Part 1's comparison table (helicopter γ = 0.99, chess γ = 0.995) — a landing sequence unfolds over many time steps, and a good or bad outcome (a safe landing, or a crash) is often only determined by the cumulative effect of many small decisions. A discount factor close to 1 keeps the agent "patient" enough to properly value how today's thruster choice affects the landing many steps later.

5. Approximating Q(s,a) with a neural network

Since there's no way to build a lookup table over a continuous state space, the approach is to train a neural network to input a state-action pair and output an approximation of Q(s,a).

The state (8 numbers) and the action, one-hot encoded (4 numbers), are concatenated into a 12-number input vector.

Input pieceEncoding
State sThe 8 raw numbers — x, y, ẋ, ẏ, θ, θ̇, l, r
Action aOne-hot: e.g. "nothing" → [1,0,0,0], "left" → [0,1,0,0], etc.
Analogy: this reframes reinforcement learning as an ordinary supervised regression problem in disguise. Instead of "input a photo, output a cat/dog label," it's "input a (state, action) pair, output a single number — how good is this pair." Section 6 explains exactly where the target numbers (the y values) for this regression come from, since — unlike ordinary supervised learning — there's no pre-existing labeled dataset to draw them from.

6. Building a training set from Bellman's equation

The Bellman equation gives exactly what's needed to create (x, y) training pairs, by treating its right-hand side as the target value the network should learn to predict:

Q(s,a) = R(s) + γ · maxa′ Q(s′,a′)    →    x = (s,a),   y = R(s) + γ · maxa′ Q(s′,a′)
1Generate experience. Take actions in the lunar lander simulator (initially at random, since there's no good policy yet) and observe tuples of (state, action, reward, next state) — written (s, a, R(s), s′).
2Turn each tuple into one training example. The first two elements (s, a) become the input x. The last two elements (R(s), s′) are enough to compute the target y, using the Bellman equation's right-hand side.
3Where does Q(s′,a′) inside the target come from, if Q isn't known yet? Initially, from a totally random guess — the neural network's own (randomly initialized) current output. This is the same "resolve the circularity" idea flagged back when Q(s,a) was first defined (Part 2, Section 2): you don't need a good Q function to get started, just some Q function, which then gets refined over many iterations.
The key conceptual leap: this is reinforcement learning wearing supervised learning's clothes. Once x and y are defined this way, training the network to predict y from x is literally the same mean-squared-error regression procedure used for ordinary supervised learning — the reinforcement learning part is entirely in how the (x, y) pairs get generated (by acting in the environment and applying the Bellman equation), not in how the network itself gets trained.

7. The full DQN algorithm

DQN stands for Deep Q-Network — using a deep neural network to learn the Q function. This is the full loop, assembled from Section 6's ingredients:

Initialize neural network randomly as a guess of Q(s,a).
Repeat {
Take actions in the lunar lander. Get (s, a, R(s), s′).
Store the 10,000 most recent (s, a, R(s), s′) tuples  (the "replay buffer")
Train model:
Create a training set of ~10,000 examples using
  x = (s,a)  and  y = R(s) + γ · maxa′ Q(s′,a′)
Train Qnew such that Qnew(s,a) ≈ y
Set Q = Qnew
}

What's a "replay buffer"?

Why only the 10,000 most recent tuples: the simulator generates far more experience than could reasonably be kept forever — potentially hundreds of thousands of steps. Keeping only a fixed-size rolling window of the most recent experience caps memory use while still providing a large, reasonably fresh training set to learn from on every round. This fixed-size rolling window of past experience is what's called a replay buffer in the reinforcement learning literature.

Why the loop actually improves Q over time

Why this converges (intuitively): on each pass, the current (possibly bad) Q is used to compute target values y, and a new network Qnew is trained to match those targets. Even though the very first Q is a random guess, R(s) — the actual reward — is always real, correct information baked into every target. Repeating this process means the "real reward" signal keeps getting propagated backward through the Bellman recursion on every iteration, so successive versions of Q become progressively better estimates of the true Q function, even though no single step required already knowing the right answer.
Going further (optional): the original DQN algorithm was introduced by Mnih et al. (DeepMind), first demonstrated learning to play Atari games directly from pixels. If you want the original technical treatment beyond what's covered in this course, searching "Human-level control through deep reinforcement learning Mnih 2015" (published in Nature) will surface the paper this algorithm is based on.

8. Refinement 1: a more efficient network architecture

The Section 5 architecture takes a single (state, action) pair as input and outputs one Q value. To compare all 4 possible actions from a given state, that requires running the network 4 separate times — once per action.

Improved: input just the 8-number state s  →  output all 4 Q-values at once: Q(s,nothing), Q(s,left), Q(s,main), Q(s,right)

The state alone is the input; the four output units each correspond to one of the four possible actions.

Why this is faster, in two separate ways: (1) When picking an action, you now need only one forward pass through the network per state, instead of four. (2) When computing the Bellman target y = R(s) + γ · maxa′Q(s′,a′) during training, you need Q(s′,a′) for every a′ to take the max — this improved architecture gives you all of those values from a single forward pass on s′, rather than four separate passes. Both the action-selection step and the target-computation step inside training get cheaper.
Note: this architecture change is described as what most real implementations of DQN actually use — it's presented as a practical efficiency improvement, not a change to the underlying math or the Bellman equation itself.

9. Refinement 2: the ε-greedy policy

While the DQN algorithm is still running (and Q is still a rough, evolving guess), it still needs to take actions in the simulator to generate more experience. How should it choose those actions?

OptionDescriptionProblem
Option 1Always pick the action that maximizes the current Q(s,a)If Q was initialized so that, say, Q(s, main) always looks low purely by chance, the agent will never try firing the main thruster — and therefore can never discover that it's actually sometimes the right move
Option 2 (ε-greedy)With probability 0.95, pick the action that maximizes Q(s,a) ("greedy," exploiting current knowledge). With probability 0.05 (ε), pick an action completely at random ("exploring")Solves Option 1's problem — occasional random actions let the agent discover that its own current beliefs about the Q function might be wrong
Analogy: this is the classic explore-vs-exploit dilemma — like choosing between your favorite restaurant (reliably good, "exploit") and trying somewhere new (might be better, might be worse, but you'll never find out otherwise, "explore"). An ε-greedy policy mostly exploits, but forces in a small, steady dose of exploration so good options never discovered by chance don't stay undiscovered forever.
The naming is famously confusing: the lecture explicitly flags that "ε-greedy" sounds like it should mean "greedy ε fraction of the time," but it actually means the opposite — greedy (1 − ε) of the time, and random (exploring) only ε of the time. Many practitioners have pointed out that "(1 − ε)-greedy" would be the more accurate name, but "ε-greedy" is the name that has stuck in the field regardless.

Decaying ε over time

A common trick: start ε high (e.g. 1.0 — meaning almost entirely random actions at the very beginning of training, when Q's guesses are worthless anyway) and gradually decrease it (e.g. down to 0.01) as training progresses. Early on there's nothing to lose by exploring heavily since the current Q estimate isn't trustworthy yet; later on, once Q has become a reasonably good estimate, it makes more sense to mostly exploit it and explore only rarely.
Why RL tuning is described as more finicky than supervised learning: the lecture makes an explicit, practical comparison — get a learning rate slightly wrong in supervised learning, and training might take 3× longer, which is annoying but survivable. Get ε (or other RL hyperparameters) noticeably wrong, and the algorithm might take 10× or 100× longer to learn, or fail to learn a good policy at all. This is attributed to reinforcement learning algorithms being comparatively less mature than supervised learning ones — worth knowing going in, so a slow or unstable first attempt at the lunar lander lab isn't mistaken for a fundamental mistake in the approach.

10. Refinement 3: mini-batching

This is actually a general supervised-learning idea (it applies to ordinary linear regression too), reused here inside the DQN loop.

The problem it solves: if your training set were, say, 100 million examples (imagine a national housing census as the analogy used in the lecture), every single step of gradient descent would require averaging the cost over all 100 million examples before taking one tiny update step. That's extremely slow — you barely move the parameters for a huge amount of computation.
Instead of using all m examples every step, use a smaller random subset m′ (e.g. 1,000) each time.
Batch gradient descentMini-batch gradient descent
Examples per stepAll m (e.g. 100 million, or all 10,000 replay-buffer tuples)A smaller subset m′ (e.g. 1,000)
Path toward the minimumSmooth, reliable — heads straight toward the minimum on every stepNoisier — sometimes even briefly heads the "wrong" way by chance — but trends toward the minimum on average
Speed per stepSlow (each step scans the whole dataset)Fast (each step only scans the mini-batch)
Analogy: polling an entire country's opinion before making any decision is thorough but painfully slow; polling a smaller random sample lets you decide much faster, with a bit more noise in each individual read — but averaged over many quick decisions, you still end up heading in the right overall direction.
Applied to DQN specifically: even though the replay buffer holds 10,000 tuples, each training round can use a smaller mini-batch (e.g. 1,000) rather than all 10,000 to build that round's training set — trading a bit of noise per update for substantially faster iterations.

11. Refinement 4: soft updates

The plain algorithm's last line — Set Q = Qnew — replaces the entire old network with the newly trained one in one abrupt step.

The problem: Qnew was just trained on one noisy mini-batch and might, purely by bad luck, turn out to be a worse estimate of the true Q function than the one it's replacing. Overwriting Q completely with a potentially-worse Qnew can make the whole learning process unstable — oscillating or even diverging instead of steadily improving.
W = 0.01 · Wnew + 0.99 · W      B = 0.01 · Bnew + 0.99 · B

Instead of fully overwriting the parameters, a soft update blends in only a small fraction (here, 1%) of the newly trained parameters, keeping 99% of the previous values.

Where the "hard update" sits as a special case: setting the blend weights to 1 and 0 instead of 0.01 and 0.99 (i.e. W = 1·Wnew + 0·W) recovers exactly the original, abrupt Set Q = Qnew behavior. The soft update is a strict generalization — 0.01/0.99 is just one particular, much gentler choice of blend weights, and those two numbers are hyperparameters you could tune, as long as they add up to 1.
Analogy: this is like updating a running average rather than replacing your best estimate with whatever the newest single measurement says. One noisy reading barely moves a running average, whereas letting a single noisy reading completely overwrite your prior estimate leaves you exposed to being thrown off course by one unlucky data point.
Why this helps convergence: the lecture states plainly that soft updates make the algorithm converge more reliably, and make oscillation or divergence less likely — a smoother, more gradual path for Q's parameters to travel, rather than a series of potentially-jarring full replacements.

12. A brief, honest note on the state of RL today

The lecture closes the week with a grounded, non-hyped perspective, worth summarizing briefly: a lot of reinforcement learning's research excitement comes from simulated environments (games, physics simulators), which are considerably easier to get working than real robots or real-world systems — many practitioners have found that an algorithm working well in simulation is no guarantee it will transfer smoothly to a physical system. Relatedly, despite heavy media coverage, RL today has far fewer practical applications than supervised or unsupervised learning — for most real-world projects, supervised or unsupervised learning is the far more likely right tool. That said, RL remains a major pillar of machine learning with real research momentum and future potential, and is well worth having in your toolkit even if it's reached for less often day-to-day than supervised learning.
