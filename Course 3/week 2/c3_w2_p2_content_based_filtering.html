1. Where Part 1 left off, and what changes now

Part 1 covered collaborative filtering: given a matrix of ratings from many users on many items, learn both the item feature vectors x^(i) and the per-user parameters w^(j), b^(j) purely from the pattern of who-rated-what. No outside information about users or items was ever used — the algorithm only "collaborates" across users' overlapping ratings.

Collaborative filtering  →  recommend based on ratings of similar users
Content-based filtering  →  recommend based on features of the user and features of the item, matched together
What stays the same: the notation r(i,j) = 1 if user j rated item i, and y(i,j) for that rating, carries over unchanged. What's different is that now we also have a feature vector describing the user and a feature vector describing the item, and the whole algorithm is built around using them.

2. Content-based filtering: the core idea

Content-based filtering recommends items by looking at features of the user and features of the item and trying to find a good match between them — rather than only looking at the pattern of ratings across many users the way collaborative filtering does.

Why this matters: collaborative filtering has no way to use anything except the ratings matrix itself. If a brand-new movie has zero ratings, or a brand-new user has rated nothing, collaborative filtering has almost nothing to work with (this is the cold-start problem from Part 1). Content-based filtering sidesteps that by using descriptive information that exists independently of the ratings — a movie's genre exists whether or not anyone has rated it yet.
Analogy: collaborative filtering is like a matchmaker who only ever asks "who liked the same things as you?" Content-based filtering is a matchmaker who actually reads your dating profile (age, interests, preferences) and reads the other person's profile, and tries to reason about why the two of you might be compatible — using the content of each profile, not just a history of who-liked-who.

3. User features and item features

Every user gets a feature vector x_u^(j), and every item gets a feature vector x_m^(i). These two vectors can be completely different lengths — nothing requires them to match in size.

User features (x_u)Example encoding
Agea number
Genderone-hot (e.g. male / female / unknown)
Countryone-hot over ~200 countries
Which of the top 1000 movies the user has watched1000 binary flags
Average rating the user has given per genreone number per genre
Movie / item features (x_m)Example encoding
Year of releasea number
Genre(s)one-hot or multi-hot
Critic reviewsone or more derived numeric features
Average rating of the moviea number
A subtlety worth pausing on: features like "average rating the user gave to romance movies" or "average rating this movie has received" are computed from the ratings themselves, yet they still count as valid content features. There's nothing circular or wrong about this — you're just summarizing the rating history into a compact number rather than using the raw ratings matrix the way collaborative filtering does directly.
Why sizes can differ: x_u might be 1500 numbers long (lots of behavioral history) while x_m is only 50 numbers long (basic movie metadata) — that's completely fine at the input stage. It only becomes a constraint once you get to the output vectors v_u and v_m (Section 4), which do have to match in size because you're about to take their dot product.

4. Learning to match: v_u and v_m

Recall the collaborative filtering prediction rule from Part 1: w^(j) · x^(i) + b^(j). Content-based filtering modifies this in two ways: it drops the bias term b^(j) entirely (this turns out not to hurt performance), and it replaces w^(j) and x^(i) with two new vectors that are both computed from features rather than treated as free parameters or given features directly.

prediction(user j, movie i)  =  v_u(j) · v_m(i)
SymbolMeaning
v_u^(j)a vector computed from x_u^(j), meant to capture user j's preferences
v_m^(i)a vector computed from x_m^(i), meant to capture movie i's characteristics
Analogy: think of v_u as a taste profile — "4.9 out of 5 on romance, 0.1 on action, 3.0 on documentaries" — and v_m as a matching content profile for the movie — "4.5 romance-ness, 0.2 action-ness, 3.5 something else." The dot product rewards a movie and a user for pointing in the same direction in this taste space; a high romance score in both multiplies together into a large positive contribution, while a mismatch (high in one, near-zero in the other) contributes almost nothing.
The one hard constraint: v_u and v_m must be the same length as each other (e.g. both length 32), even though the raw feature vectors x_u and x_m that produced them can be completely different lengths. A dot product is only defined between vectors of matching dimension.

The open question this leaves: given raw features x_u and x_m of possibly very different sizes, how do you actually compute v_u and v_m so that they land in the same 32-dimensional space and so that their dot product is a good rating predictor? That's what Section 5 answers.

5. Deep learning architecture (twin networks)

The standard, commercially-used way to compute v_u and v_m is to run each raw feature vector through its own neural network — a user network and a movie (item) network — each ending in an output layer of exactly 32 units, so both networks' outputs land in the same 32-dimensional space no matter how different their inputs were.

The user network and movie network, drawn as one combined architecture ending in a dot product.

1User network: takes x_u (age, gender, country, watch history, ...) through a few Dense layers, ending in an output layer of 32 units → v_u.
2Movie network: takes x_m (year, genre, reviews, average rating, ...) through its own Dense layers — which can have a different number of layers or units than the user network — ending in an output layer of 32 units → v_m.
3Combine: take the dot product v_u · v_m as the predicted rating. For binary labels (did the user like / click / favorite the item), apply a sigmoid to the dot product: g(v_u · v_m) gives the predicted probability that y(i,j) = 1.
Why draw two separate networks as "one architecture": the lecture material makes a point of this — neural networks are easy to compose. You can take two independently-designed networks (different depths, different widths, tailored to their own very different input types) and bolt them together at the end with a simple operation like a dot product, and train the whole thing jointly. This same idea of combining sub-networks reappears throughout deep learning wherever you have two different kinds of input that need to be compared or matched.
No separate training procedure: there isn't a "train the user network first, then the movie network." Both networks' parameters are trained together, using one shared cost function (Section 6) — gradient descent updates every layer in both networks simultaneously based on how well the final dot product matches the true ratings.

6. The cost function for content-based filtering

J  =  ∑(i,j): r(i,j)=1 (v_u(j) · v_m(i) − y(i,j))²  +  NN regularization term

This is deliberately close to the collaborative filtering cost function from Part 1 — sum the squared error between predicted and actual rating, over only the (i, j) pairs where a rating actually exists (r(i,j) = 1), plus a regularization term (the usual neural-network weight-penalty, applied to the parameters of both networks) to discourage overfitting.

Why this matters: the entire content-based filtering system — both networks' worth of weights — is trained by minimizing this one cost function with gradient descent (or Adam, see Section 8). There's no hand-crafted rule for what v_u or v_m "should" contain; the training process is what discovers vectors such that their dot products line up with real ratings.

7. Finding similar items (again)

Exactly as in collaborative filtering (Part 1, Section 9), once you've trained the movie network and computed v_m(i) for every movie, you can find movies similar to movie i by looking for other movies k with small squared distance between their learned vectors.

distance(k, i)  =  ||v_m(k) − v_m(i)||²
Contrast with Part 1: in collaborative filtering this same idea used the learned item features x^(k) and x^(i) directly (there was no separate v — the learned x was the representation). Here, x_m is the raw, human-readable feature vector (year, genre, reviews...) and v_m is what the movie network computes from x_m — so it's v_m, not x_m, that plays the role of "the learned representation" this time.
Can be pre-computed: because v_m for every movie only depends on that movie's own features (not on any particular user), you can compute the full similar-items table for your entire catalog offline, overnight, and just look results up instantly when a user is browsing. This pre-computability becomes important again in Section 9.

8. TensorFlow implementation, step by step

This mirrors the pattern from Part 1's TensorFlow section (declare the model, define how data flows through it, pick an optimizer, train) but here the "model" is the two-tower architecture from Section 5, built with the ordinary Sequential/Functional Keras API rather than hand-written GradientTape loops, since content-based filtering's forward pass is just an ordinary stack of Dense layers (twice) plus a dot product — unlike collaborative filtering's cost function, which didn't fit the standard layer-stack pattern.

1Define the user network and item (movie) network as two ordinary Sequential models. Both end in a Dense layer of 32 units with no activation — that final layer is v_u / v_m, so it's left as raw numbers rather than passed through relu or sigmoid.
user_NN = tf.keras.models.Sequential([
    tf.keras.layers.Dense(256, activation='relu'),
    tf.keras.layers.Dense(128, activation='relu'),
    tf.keras.layers.Dense(32)
])

item_NN = tf.keras.models.Sequential([
    tf.keras.layers.Dense(256, activation='relu'),
    tf.keras.layers.Dense(128, activation='relu'),
    tf.keras.layers.Dense(32)
])
2Wire up the inputs and pass them through each network, then L2-normalize each output vector to length 1.
# create the user input and point to the base network
input_user = tf.keras.layers.Input(shape=(num_user_features))
vu = user_NN(input_user)
vu = tf.linalg.l2_normalize(vu, axis=1)

# create the item input and point to the base network
input_item = tf.keras.layers.Input(shape=(num_item_features))
vm = item_NN(input_item)
vm = tf.linalg.l2_normalize(vm, axis=1)
Why normalize to length 1? The lecture flags this as an extra step that "makes the algorithm work a bit better" — without it, the dot product's magnitude is free to grow simply by the network learning large-magnitude vectors, rather than by genuinely capturing direction/alignment between user taste and item content. Normalizing to unit length forces the dot product to depend only on the angle between v_u and v_m (their cosine similarity), which is a cleaner signal of "how well matched are these two."
3Take the dot product using Keras's dedicated Dot layer (distinct from a plain Dense layer — this one has no trainable weights, it purely computes v_u · v_m for each pair fed to it).
# measure the similarity of the two vector outputs
output = tf.keras.layers.Dot(axes=1)([vu, vm])
4Assemble the full model by telling Keras what the inputs and output are, then compile with mean squared error.
# specify the inputs and output of the model
model = Model([input_user, input_item], output)

# Specify the cost function
cost_fn = tf.keras.losses.MeanSquaredError()
Why this is simpler than Part 1's TensorFlow section: collaborative filtering needed a hand-written cost function plus an explicit GradientTape loop because its structure (a shared X, W, b jointly indexed by both movies and users) doesn't correspond to any standard Keras layer stack. Content-based filtering's forward pass — two towers of Dense layers meeting at a Dot layer — is exactly what Keras's ordinary Model/Sequential machinery is built for, so it can be trained with the standard model.compile() / model.fit() workflow instead.

9. Recommending from a large catalog: retrieval & ranking

A real streaming site might have thousands of movies; an ad system might choose from millions of ads; a music service might have tens of millions of songs; a shopping site might have tens of millions of products. Running the full user-network-then-dot-product computation against every single item every time a user loads the page is computationally infeasible at that scale.

Why this matters: the fix isn't a different model — it's a different pipeline. Large-scale recommender systems split the work into two stages: a cheap, broad retrieval step that narrows millions of items down to a few hundred plausible candidates, followed by an expensive, precise ranking step that only has to run the full neural network on that much smaller shortlist.

The two-step pipeline: retrieval narrows the catalog broadly and cheaply; ranking scores that shortlist precisely.

Retrieval step — generate a broad candidate list

Goal: cast a wide net. It's fine (even expected) that many retrieved items turn out to be ones the user won't like — the only real failure mode at this stage is missing the good options. Example retrieval rules from the lecture:

1For each of the last 10 movies the user watched, find the 10 most similar movies (using the pre-computed ||v_m^(k) − v_m^(i)||² distances from Section 7).
2For the user's top 3 most-viewed genres, find the top 10 movies in each genre.
3Find the top 20 movies in the user's country.

Combine everything retrieved into one list, removing duplicates and removing items the user has already watched or purchased. This whole step is fast and can produce on the order of hundreds of candidates.

Ranking step — score the shortlist precisely

Take the (much smaller) list from retrieval and run it through the trained model: feed in the user feature vector and each candidate item's feature vector, compute the predicted rating (or probability, for binary labels) for every user-item pair, and sort by that score. Display the top results to the user.

The key computational shortcut: if v_m has already been pre-computed for every item in the catalog (Section 7's point about pre-computability), the ranking step doesn't need to re-run the movie network at all — it only needs one forward pass through the user network (to get v_u for whoever is currently on the site) and then a fast dot product against each candidate's already-known v_m. This is what makes the ranking step tractable even though it's the "expensive, precise" half of the pipeline.

10. The retrieval/ranking trade-off

The one knob you control is how many items to retrieve before handing them to ranking — e.g. 100 vs. 500 vs. 1000.

Retrieve more itemsRetrieve fewer items
Better recommendation quality (ranking has more good candidates to choose from)Faster response time
Slower, since ranking must score every retrieved candidateRisk of missing a genuinely good item that retrieval didn't surface
How to actually decide the number: don't guess — run offline experiments. Check whether retrieving more items (say, 500 instead of 100) meaningfully raises P(y(i,j) = 1) — i.e., whether the extra candidates you'd be adding are actually ones the model predicts the user will rate highly / engage with. If going from 100 → 500 barely moves that number, it's not worth the added latency. If it moves it a lot, the slower response may be worth it.
Why this two-step design matters commercially: it's precisely this split — broad-and-cheap retrieval followed by narrow-and-precise ranking — that lets today's large-scale recommender systems be both fast and accurate simultaneously, despite catalogs of millions of items. Neither goal is achievable alone: ranking all items precisely is too slow; retrieving without a ranking step is too imprecise.

11. Ethical use of recommender systems

How you define the goal the recommender system optimizes for has real consequences — some choices are clearly fine, others deserve real scrutiny.

Possible optimization goalConcern level
Movies most likely to be rated 5 stars by the userGenerally fine
Products most likely to be purchasedGenerally fine
Ads most likely to be clicked on, weighted by advertiser bid⚠ Worth scrutiny
Products that generate the largest profit for the company⚠ Worth scrutiny
Videos that lead to maximum watch time⚠ Worth scrutiny

Worked example: advertising as an amplifier

The advertising industry can amplify either very good or very harmful businesses, through the same feedback loop mechanism, depending on what's being amplified:

The same ad-bidding mechanism creates a virtuous cycle for a good-faith business and a harmful cycle for an exploitative one.

Why the mechanism itself is neutral but the outcome isn't: a business that's good at serving customers becomes more profitable, which lets it bid higher for ads, which drives it more traffic, which reinforces the cycle — good for a travel company built on real value. But the identical mechanism rewards a payday-loan company that is simply efficient at extracting money from vulnerable customers: efficiency at exploitation is still efficiency, so it too becomes more profitable, bids higher, and gets more traffic. The recommender/ad system can't tell "profitable because it serves people well" apart from "profitable because it exploits people well" unless something is explicitly built in to distinguish them.

Other problematic patterns and possible ameliorations

ProblemPossible ameliorationWhy it's still hard
Maximizing watch-time/engagement can amplify conspiracy theories and toxic content, since that content is often highly engagingFilter out clearly harmful content (hate speech, fraud, scams, certain violent content)Defining exactly what counts as "problematic content" to filter is itself a genuinely difficult, contestable line to draw
Ad systems amplifying exploitative businesses (payday loans, etc.)Refuse ads from exploitative businessesDefining "exploitative" precisely enough to apply consistently is hard
Users often don't realize a site is optimizing for the company's profit rather than the user's actual interestBe transparent with users about what criteria are driving recommendationsRequires companies to voluntarily disclose business-sensitive optimization choices
The honest takeaway from the lecture: there's no clean, easy technical fix for most of these problems — they require judgment calls (what counts as "exploitative," what counts as content worth filtering), and the material explicitly frames this as something that should involve diverse perspectives, open discussion, and ongoing debate rather than a one-time rule anyone can just implement and be done with.
Going further (not required, but useful if you want more depth): the lecture doesn't cite specific external readings, but if you want to explore the amplification-of-harmful-content problem in more depth, searching for reporting on "recommender system radicalization" or "engagement-optimization and misinformation" (e.g. coverage of YouTube's or social platforms' recommendation algorithms) will surface real case studies that make the abstract "engagement vs. harm" trade-off concrete.
