1. Where we're coming from

Back with one feature, the model was f(x) = w·x + b, with one w and one b. Now we have multiple features — say a house has size, number of bedrooms, age, etc. That means we need one weight per feature: w₁, w₂, ..., wₙ, plus the same single b as before.

The model becomes:

f(x) = w₁x₁ + w₂x₂ + ... + wₙxₙ + b

That's fine, but writing out a long sum every time — for the model, for the cost function, for every gradient descent update — gets messy fast. That messiness is the actual problem this lesson solves.

2. Rewriting everything with vectors

Instead of treating w₁ through wₙ as n separate numbers, just line them up into one object:

w = [w₁  w₂  ...  wₙ]   →  a vector of length n

b stays exactly as it was — just one plain number, not part of the vector. Only the weights got bundled together, because there's one weight per feature, but only one bias for the whole model.

Why bother bundling w₁...wₙ into one vector w?
Not for a new mathematical trick — it's a notational compression. It lets you write one version of the model/cost/gradient-descent formulas that automatically works whether you have 2 features or 200. And practically, it maps directly onto NumPy: w becomes a 1-D array, and operations on it become fast vectorized NumPy operations instead of slow Python loops (this is the "vectorization" part from the previous lab).

The model, in vector form

The long sum w₁x₁ + w₂x₂ + ... + wₙxₙ is literally the definition of a dot product. So:

f(x) = w · x + b

Same model. Just written compactly — the dot (·) silently does the "multiply matching elements, then add them all up" work for you.

The cost function, in vector form

BeforeNow
J(w₁, ..., wₙ, b)J(w, b)

Nothing changed about what the cost function computes. It's the exact same "how far off are my predictions" measure. Only the input list got replaced by a single vector.

3. Gradient descent itself: one feature vs n features

This is the part worth slowing down on, because it's easy to think something new is happening here — it isn't. Compare side by side:

One featuren features (n ≥ 2)
w = w − α · (1/m)Σ(f(x⁽ⁱ⁾) − y⁽ⁱ⁾)x⁽ⁱ⁾ wⱼ = wⱼ − α · (1/m)Σ(f(x⁽ⁱ⁾) − y⁽ⁱ⁾)xⱼ⁽ⁱ⁾   for j = 1...n
b = b − α · (1/m)Σ(f(x⁽ⁱ⁾) − y⁽ⁱ⁾) b = b − α · (1/m)Σ(f(x⁽ⁱ⁾) − y⁽ⁱ⁾)

Read the update rule for w piece by piece — it's the same recipe both times:

1
Error term: f(x⁽ⁱ⁾) − y⁽ⁱ⁾ — how wrong was the prediction for training example i. Same in both columns.
2
Multiply by the matching feature value: single-feature version multiplies by x⁽ⁱ⁾; multi-feature version multiplies by xⱼ⁽ⁱ⁾ — just feature j of example i, instead of "the one and only feature."
3
Average over all m examples — the sum and the 1/m, unchanged.
4
Scale by the learning rate α and subtract — unchanged.

The only real difference: with one feature you had one update rule for the weight. With n features, you have the same update rule repeated n times — once for each wⱼ, each time using that feature's own column of data (xⱼ) but the exact same error term. b's update doesn't even change, since there's only ever one b.

Why does the b update rule look identical, but w's split into n copies?
Because b affects the prediction the same way regardless of feature — it's just added on. But each wⱼ only touches its own feature xⱼ, so the "how much should this specific weight move" question is naturally a separate calculation per feature. That's really just calculus: the partial derivative of J with respect to wⱼ only involves xⱼ.

All updates for w₁ ... wₙ and b happen simultaneously — you compute all the new values first using the old w, b, then update everything at once, not one after another using already-updated values.

Why this connects back to vectorization

Written with vector notation, the whole block of n update rules for w₁...wₙ collapses into one line:

wⱼ = wⱼ − α · ∂/∂wⱼ J(w, b)

and in code, that "loop over j = 1 to n" is exactly what NumPy's vectorized operations replace with one fast array operation — the payoff of the previous lab's speed comparison (np.dot vs. a manual Python for loop) is precisely why this matters in practice.

4. The normal equation — a side note, not the main method

There's a second way to solve for w and b in linear regression specifically, called the normal equation: a direct linear-algebra solve, no iteration needed.

Why not just always use the normal equation instead of gradient descent?
  • It only works for linear regression — not logistic regression, not neural networks, not anything else you'll meet later.
  • It gets slow when the number of features is large.
  • You'll basically never implement it yourself — but some mature ML libraries may use it under the hood, so it's worth recognizing the term (including, e.g., in an interview).
Gradient descent is the general-purpose tool; the normal equation is a linear-regression-only shortcut.

5. Lab02 code: same formulas, in NumPy

Data: X_train shape (m, n) = 3 examples × 4 features (size, bedrooms, floors, age). w shape (n,), b scalar.

Prediction — f(x) = w·x + b

fw,b(x) = w · x + b = w₀x₀ + w₁x₁ + ... + wn−1xn−1 + b
p = np.dot(x, w) + b

Replaces a manual loop (predict_single_loop) that multiplies each x[i] by w[i] and sums. Same result, one line.

Cost — J(w, b)

J(w,b) = (1 / 2m) · Σi=0m−1 ( fw,b(x⁽ⁱ⁾) − y⁽ⁱ⁾ )²
for i in range(m):
  f_wb_i = np.dot(X[i], w) + b
  cost += (f_wb_i − y[i])**2
cost = cost / (2*m)

This is the formula directly: loop over the m examples, still using the vectorized dot product per example.

Gradient — ∂J/∂wⱼ and ∂J/∂b

∂J(w,b)/∂wⱼ = (1/m) · Σi=0m−1 ( fw,b(x⁽ⁱ⁾) − y⁽ⁱ⁾ ) xⱼ⁽ⁱ⁾
∂J(w,b)/∂b = (1/m) · Σi=0m−1 ( fw,b(x⁽ⁱ⁾) − y⁽ⁱ⁾ )
for i in range(m):
  err = np.dot(X[i], w) + b − y[i]
  for j in range(n): dj_dw[j] += err * X[i, j]
  dj_db += err
dj_dw /= m ; dj_db /= m

This is exactly the wⱼ-repeated-n-times pattern from Section 3: outer loop over examples computes the error once, inner loop over features applies that same error to each xⱼ. dj_db needs no inner loop — one b, so it just accumulates.

Gradient descent loop

repeat until convergence: { wⱼ = wⱼ − α · ∂J(w,b)/∂wⱼ   (for j = 0..n−1)    b = b − α · ∂J(w,b)/∂b }
dj_db, dj_dw = compute_gradient(X, y, w, b)
w = w − alpha * dj_dw   # updates all n weights at once
b = b − alpha * dj_db

w − alpha * dj_dw is NumPy doing simultaneous update for free — subtracting two arrays updates every wⱼ in one line, no explicit loop needed at this level.

Why the run in the lab looks bad (cost barely drops after 1000 iterations)
Size is in raw sqft (~2000) while bedrooms/floors are ~1-5 — wildly different scales. Gradient descent has to use a tiny learning rate (5e-7) to avoid diverging, which makes it crawl. Fixed next lab via feature scaling.

6. One-paragraph summary

Multiple linear regression just means one weight per feature instead of one weight total. Bundling w₁...wₙ into a single vector w doesn't change the math — it lets the model become w·x + b (a dot product) and lets gradient descent be written as one compact update rule instead of n separate ones. Under the hood, gradient descent with n features is literally the single-feature update rule, repeated once per feature, using that feature's own data column each time, while b's rule stays exactly the same since there's only one of it. The normal equation is a separate, linear-regression-only alternative to gradient descent — good to recognize, not something you'll typically build yourself.
