1. Feature scaling — why & how

The problem

Say you're predicting house price from x1 = size (300–2000 sqft) and x2 = bedrooms (0–5). Because x1 is a much bigger number than x2, a *good* model ends up needing a *tiny* w1 (like 0.1) and a *large* w2 (like 50), just so both terms land in a sensible range when predicting price.

Why does that break gradient descent?
Because w1 gets multiplied by a huge number (up to 2000), even a tiny nudge to w1 swings the cost a lot — the cost function is very sensitive to w1. w2 gets multiplied by a small number (up to 5), so the cost is much less sensitive to it. Plotted as a contour map (rings = equal-cost levels, like elevation lines), this produces a tall, narrow, elongated bowl instead of a nice round one.

Gradient descent takes steps roughly perpendicular to the contour lines. On the skinny bowl, that direction doesn't point at the center — so the path bounces back and forth (zig-zags) while making slow overall progress. On the round bowl, it heads almost straight for the minimum.

Three ways to scale

MethodFormulaNotes
Max (divide by max) x' = x / x_max Simplest. Result lands in (0, 1] if all values ≥ 0.
Mean normalization x' = (x − μ) / (x_max − x_min) Centers data around 0; range roughly [−1, 1].
Z-score normalization x' = (x − μ) / σ μ = mean, σ = standard deviation. Most commonly used in practice (and in Lab03/Lab04).
Rule of thumb: aim for each feature roughly in [−1, 1] (loosely — [−3, 3] or [−0.3, 0.3] are fine too). If a feature's range is already small (like [−2, 0.5]), scaling is optional. If it's huge (like [−100, 100]) or tiny (like [−0.001, 0.001]) compared to other features, scale it. There's almost never harm in scaling — when in doubt, do it.

2. Checking gradient descent for convergence

The tool: plot cost J (vertical axis) against iteration number (horizontal axis) — not against a parameter like w. This is called a learning curve.

Reading the curve: a flattening curve (e.g. barely moving after iteration ~300–400) signals gradient descent has more or less converged. The exact number of iterations needed varies enormously between problems — sometimes 30, sometimes 100,000 — which is exactly why you look at the curve instead of guessing a fixed number in advance.

Automatic convergence test: declare convergence if J drops by less than a small threshold ε (e.g. 0.001) in one iteration. In practice, picking a good ε is fiddly, so eyeballing the learning curve is usually more reliable.

Key debugging fact: with a small enough learning rate, J should decrease on every single iteration — no exceptions. If J ever goes up, either α is too large, or there's a bug (classic bug: writing w = w + α·∂J/∂w instead of w = w − α·∂J/∂w, which walks away from the minimum).

3. Choosing the learning rate α

If α is too small, gradient descent works correctly but crawls — needs a huge number of iterations. If α is too large, each step can overshoot the minimum, causing J to bounce or even increase every iteration.

Practical search strategy

Try a range of values, each roughly 3× the previous: 0.001 → 0.003 → 0.01 → 0.03 → 0.1 → ... Run gradient descent for just a handful of iterations at each, plot J vs. iterations, and find:

  1. The largest α that's clearly too large (J bounces/increases)
  2. The smallest α that's clearly too small (barely moves)
  3. Pick close to the largest value that still decreases J rapidly and consistently
Debugging trick: set α to something extremely small on purpose. If J still doesn't decrease every iteration even then, the problem isn't α — it's a bug in the code (not a tuning issue).

Z-score normalization in code

μⱼ = mean of column j    σⱼ = std of column j    X_norm[:,j] = (X[:,j] − μⱼ) / σⱼ

axis=0 means "compute the mean/std down each column" — i.e., per feature, across all m examples — matching the formula's per-feature μⱼ, σⱼ.

5. Feature engineering

Feature engineering = using domain knowledge to create new, more useful features from the ones you already have — usually by transforming or combining original features.

Classic example: given lot width (x1) and depth (x2), you might suspect the area matters more for price than width/depth separately. So engineer:

x3 = x1 × x2   (area)
f(x) = w1·x1 + w2·x2 + w3·x3 + b

Gradient descent then decides — via the learned weights — whether width, depth, or area (or some mix) is actually most predictive. This one idea (engineering new features from existing ones) is also the gateway to fitting curves, not just straight lines — that's polynomial regression, next.

6. Polynomial regression + Lab04, explained slowly

Let's start from the actual problem, not the terminology. Forget "polynomial regression" as a phrase for a second.

Step 1 — the problem in one picture

You have data that looks like a curve. A straight line, no matter how you rotate/shift it, can never bend to match a curve. That's it — that's the entire motivation.

Step 2 — the actual trick (this is the only idea in the whole topic)

Linear regression can only draw straight lines with respect to whatever features you hand it. So instead of changing the algorithm, we trick it: we hand it a new feature, x², instead of (or alongside) x.

Old model:  f(x) = w·x + b    → always a straight line
New model:  f(x) = w1·x + w2·x² + b    → can bend into a curve
Why does adding x² let a "straight-line algorithm" draw a curve?
Gradient descent doesn't know or care what x and x² "mean." It just sees two numbers per example and finds the best w1, w2, b to combine them. Since x² grows differently than x (1, 4, 9, 16, 25... instead of 1, 2, 3, 4, 5...), multiplying it by a weight and adding it in bends the output curve — even though, from the algorithm's point of view, it's still doing the exact same "weights times features, summed" computation as always. Nothing about gradient descent changed. We just gave it a more useful input.

Step 3 — why "linear" regression can still draw a curve (this is the confusing part)

"Linear" describes how the parameters (w1, w2, b) enter the formula — each one is just multiplied by something and added, never squared, never multiplied by each other. It says nothing about whether the resulting graph is a straight line.

Look at the formula two different ways — once treating x as the variable, once treating w as the variable:

View 1 — is it linear in x?
f(x) = w1·x + w2·x² + b

No. x appears squared. That's exactly what bends the graph into a curve when you plot f against x.

View 2 — is it linear in w?
f(w1, w2) = x·w1 + x²·w2 + b

Yes. Relabel x as "a" and x² as "c" (just numbers once you plug in a data point) — it's literally a·w1 + c·w2 + b. Just weights, multiplied by known numbers, added up. No w², no w1·w2, nothing.

Gradient descent's entire job is to search over w1, w2, b — it never touches x. So the question that actually matters for "is this linear regression" is View 2, not View 1. That's the whole trick, made concrete:

xx² (the engineered feature)f = w1·x + w2·x² + b, with w1=1, w2=1, b=0
111·1 + 1·1 = 2
241·2 + 1·4 = 6
391·3 + 1·9 = 12
4161·4 + 1·16 = 20

Look at the output column: 2, 6, 12, 20 — the gaps between them (4, 6, 8) are growing, not constant. A straight line always has constant gaps. This growing-gap pattern is precisely what makes the plotted graph curve upward, even though every single step of computing it was just "multiply by a weight, add" — genuinely linear arithmetic in w.

One-line version to remember: the algorithm (gradient descent, the update rule, the whole "machinery") only ever sees numbers times weights, summed — it's blind to the fact that one of those numbers happens to be another number squared. The curve is a side effect of what you fed in, not something the algorithm does differently.

Notice: x² is always positive (a negative x, once squared, still adds a positive number) — that's why a pure quadratic eventually curls back down on both ends, like a U or an upside-down U. x³ keeps the sign of x — negative x stays negative, positive x stays positive — so a cubic term keeps pushing the curve in one consistent direction instead of curling back.

So the choice isn't arbitrary — you're picking a shape family based on which one won't produce nonsense predictions at the edges of your data (like a giant mansion predicted to cost less than a small house).

Confirming exactly what you said: correct on both counts.

MethodGradient descent (iterative)Normal equation (direct solve)
Needs iterations?Yes — max_iter, runs a loopNo — solves in one shot
Needs feature scaling?Yes, strongly recommendedNo, not required
Importfrom sklearn.linear_model import SGDRegressorfrom sklearn.linear_model import LinearRegression
model = LinearRegression()
model.fit(X_train, y_train)  # no scaling needed, no alpha, no iterations
w = model.coef_
b = model.intercept_
Why does LinearRegression skip scaling and iterating entirely?
Because it isn't searching/stepping toward the answer the way gradient descent does. The normal equation solves for w, b directly using linear algebra — essentially one matrix computation that lands exactly on the minimum of the cost function in a single step. There's no "step size" (α) because there are no steps, and no scaling problem because there's no zig-zagging contour path to worry about (that whole problem, from Section 1, only exists *because* gradient descent takes iterative steps).

Why not always use LinearRegression / the normal equation then, if it's simpler? Same trade-off flagged back in Section 3 of your very first reference file: it only works for plain linear regression (not logistic regression, not neural nets), and it gets slow when the number of features is large, since the underlying matrix math scales poorly. Gradient descent (what SGDRegressor uses) is the general-purpose tool that scales to those other algorithms; the normal equation is a linear-regression-only shortcut.

8. One-paragraph summary of the whole week

Multiple linear regression generalizes single-feature regression by bundling weights into a vector, letting the model and gradient descent be written compactly using dot products. When features have very different scales, gradient descent's cost surface becomes a narrow, skewed bowl and convergence gets slow or unstable — feature scaling (max-normalize, mean-normalize, or Z-score) fixes this by putting all features on comparable ranges. Plotting cost vs. iteration (a learning curve) is how you check whether gradient descent is actually converging and whether the learning rate α is well chosen — too small crawls, too large overshoots or diverges. Feature engineering — creating new features from existing ones, including powers like x² and x³ — lets this same linear-regression machinery fit curves instead of just straight lines (polynomial regression), with feature scaling becoming even more essential since engineered powers can have drastically different ranges.
