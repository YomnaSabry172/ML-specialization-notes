1. Gradient Descent for Logistic Regression

Just like linear regression, fitting logistic regression means finding the parameters w and b that minimize the cost function J(w,b) you built in the previous part of this week (the log-loss cost). The tool to do that minimization is, again, gradient descent.

Gradient descent — general update rule (repeat until convergence) wj = wj − α · ∂J(w,b)/∂wj   (for j = 1...n)
b = b − α · ∂J(w,b)/∂b

Working out the calculus (which the course doesn't require you to derive by hand) gives these derivative terms:

The gradients for logistic regression ∂J/∂wj = (1/m) Σi=1m [ (f(x⁽ⁱ⁾) − y⁽ⁱ⁾) · xj⁽ⁱ⁾ ]
∂J/∂b = (1/m) Σi=1m [ f(x⁽ⁱ⁾) − y⁽ⁱ⁾ ]

Here, (f(x⁽ⁱ⁾) − y⁽ⁱ⁾) is the error term — how far the model's prediction is from the true label, for example i. The w_j gradient multiplies that error by the j-th feature value; the b gradient just uses the error directly (no feature multiplied in).

Don't forget: simultaneous updates Exactly like linear regression, you must compute the right-hand sides for all parameters (every w_j and b) first, using the old values, and only then overwrite them all at once. Updating w_1 and then using the new w_1 to compute the update for w_2 in the same iteration is a subtle bug.

2. Why This "Looks the Same" as Linear Regression — But Isn't

If you compare these update equations to the ones from linear regression in Week 2, they look identical on the page. This naturally raises the question: is logistic regression secretly the same algorithm as linear regression?

Linear regression

f(x) = w · x + b

f(x) is a raw, unbounded number.

Logistic regression

f(x) = g(w · x + b) = 1/(1+e−z)

f(x) is squashed through the sigmoid — always between 0 and 1.

Why this matters The two algorithms are genuinely different because f(x) means something different in each — a real number vs. a probability. The update-rule formulas happen to have the same algebraic shape only because both cost functions were specifically designed (squared error for linear regression, log-loss for logistic regression) so that their derivatives simplify to this same clean "error times feature" pattern. Same-looking formula, completely different model hiding inside f(x).

3. Quick Preview — Ideas Reused From Linear Regression

The lecture flags three techniques from Week 2's linear regression material that carry over to logistic regression without any real change, and says they'll be explored in more depth later in the specialization. Brief previews so you have the vocabulary now:

Monitor convergence (learning curve)

Plot J(w,b) against the iteration number while gradient descent runs. If it's steadily decreasing and flattening out, gradient descent is converging; if it jumps around or increases, your learning rate α is probably too large.

Vectorized implementation

Instead of looping over training examples in Python (as Lab 6's compute_gradient_logistic does for clarity), express the same computation as matrix/vector operations in NumPy. Same math, much faster execution.

Feature scaling

Rescaling features to a similar range (e.g., roughly −1 to 1) before training helps gradient descent take more direct steps toward the minimum, so it converges faster — same benefit it gave linear regression.

4. Deep Dive — Lab 6: Gradient Descent for Logistic Regression

C1_W3_Lab06_Gradient_Descent_Soln.ipynb

The gradient computation, line by line

def compute_gradient_logistic(X, y, w, b):
    """
    Computes the gradient for logistic regression

    Args:
      X (ndarray (m,n): Data, m examples with n features
      y (ndarray (m,)): target values
      w (ndarray (n,)): model parameters
      b (scalar)      : model parameter
    Returns
      dj_dw (ndarray (n,)): The gradient of the cost w.r.t. the parameters w.
      dj_db (scalar)      : The gradient of the cost w.r.t. the parameter b.
    """
    m,n = X.shape
    dj_dw = np.zeros((n,))
    dj_db = 0.

    for i in range(m):
        f_wb_i = sigmoid(np.dot(X[i],w) + b)
        err_i  = f_wb_i  - y[i]
        for j in range(n):
            dj_dw[j] = dj_dw[j] + err_i * X[i,j]
        dj_db = dj_db + err_i
    dj_dw = dj_dw/m
    dj_db = dj_db/m

    return dj_db, dj_dw
CodeMatches which formula piece
f_wb_i = sigmoid(np.dot(X[i],w) + b)f(x⁽ⁱ⁾) = g(w·x⁽ⁱ⁾ + b) — the model's prediction for example i
err_i = f_wb_i - y[i]The error term (f(x⁽ⁱ⁾) − y⁽ⁱ⁾) shared by both gradient formulas
inner loop: dj_dw[j] += err_i * X[i,j]Accumulating Σ (error × xj⁽ⁱ⁾) for the wj gradient
dj_db = dj_db + err_iAccumulating Σ (error) for the b gradient
dj_dw = dj_dw/m, dj_db = dj_db/mThe (1/m) averaging factor outside both sums

The gradient descent loop

def gradient_descent(X, y, w_in, b_in, alpha, num_iters):
    J_history = []
    w = copy.deepcopy(w_in)   # avoid modifying the caller's array
    b = b_in

    for i in range(num_iters):
        dj_db, dj_dw = compute_gradient_logistic(X, y, w, b)
        w = w - alpha * dj_dw
        b = b - alpha * dj_db

        if i<100000:
            J_history.append( compute_cost_logistic(X, y, w, b) )
        if i% math.ceil(num_iters / 10) == 0:
            print(f"Iteration {i:4d}: Cost {J_history[-1]}   ")

    return w, b, J_history
Note the clean separation of concerns compute_gradient_logistic only computes the direction/size of the step (the math from Section 1). gradient_descent only handles the repeat-loop bookkeeping: apply the step, log the cost, print progress. This split is exactly why the lecture says "the loop is generally provided to you" while "the gradient calculation... you will be asked to implement" — they are two genuinely separate jobs, and the practice lab will only ask you to write the first one.

Why copy.deepcopy(w_in) matters

Without this, w = w_in would just make w point to the exact same NumPy array the caller passed in. Modifying w inside the function would then silently modify the caller's original array too — a classic Python/NumPy mutability trap. deepcopy makes an independent copy so the function is safe to call without side effects.

Running it & reading the plot

b_tmp  = 0.
alph = 0.1

6. The Problem of Overfitting

A trained model can go wrong in two opposite ways. Both are best understood through the housing-price regression example (price vs. house size).

Same 5 training points, three different polynomial degrees fit to them.

Underfitting (high bias)"Just right"Overfitting (high variance)
Model usedStraight line (degree 1)Quadratic (degree 2)4th-order polynomial (degree 4)
Fit to training dataPoor — misses the obvious flattening patternGood, not perfectPerfect — passes through every point, cost = 0
Generalizes to new houses?No — wrong shape entirelyYes, reasonably wellNo — wildly wiggly between points
Why this matters Training cost of exactly 0 sounds like a perfect model, but it's actually a red flag: it usually means the model has memorized the noise in this specific training set rather than learning the real underlying pattern. The entire goal of machine learning is generalization — good predictions on new, unseen examples — not a perfect score on data the model has already seen.
Analogy — Goldilocks Underfitting is porridge too cold: the model didn't even try hard enough to match the shape of the data (too strong a "preconception" that it must be linear). Overfitting is porridge too hot: the model tried so hard to match every single data point exactly that it twisted itself into an unreasonable, overly wiggly shape. The quadratic fit is porridge that's just right — close to the data without chasing every bit of noise.

The two technical-term pairs (used interchangeably)

Pair 1Pair 2Meaning
UnderfittingHigh biasThe model has too strong a "preconception" about the data's shape and can't capture the real pattern even in the training data.
OverfittingHigh varianceThe model is so flexible that tiny changes in the training set would produce wildly different fitted curves — high variability across different possible training sets.
Terminology note "Bias" here is a technical statistical term (about how well a model's assumptions match reality) — not the same as "bias" meaning unfair discrimination against groups like gender or ethnicity, which is a separate and equally important concept in ML but not what's meant in this context.

The same problem in classification

Overfitting isn't unique to regression — it happens with logistic regression's decision boundary too, using the same tumor-classification setup (x₁ = tumor size, x₂ = age):

Crosses = malignant (y=1), circles = benign (y=0). Same three-way pattern as regression: line → ellipse → overly-twisted boundary.

  • Underfit: only raw features (x₁, x₂) → decision boundary can only be a straight line → doesn't separate the classes well.
  • Just right: add quadratic features (x₁², x₂²) → boundary becomes an ellipse → separates classes well, misclassifying only a few points, generalizes well.
  • Overfit: many high-order polynomial features → boundary twists to perfectly enclose every training point → unlikely to generalize to new patients.

8. Addressing Overfitting — Three Strategies

1. Collect more data

With more training examples, even a high-order polynomial is forced to fit a smoother, less wiggly curve, because it now has to satisfy many more constraints at once.

Limitation: more data isn't always available (e.g. only so many houses have sold in a given area).

2. Feature selection

If you have many features (e.g. 100 features per house) but limited data, keep only the most relevant subset (e.g. size, bedrooms, age) and drop the rest.

Limitation: you throw away information — some of the dropped features might have actually been useful.

3. Regularization

Keep all the features, but shrink the size of the parameters w_j so no single feature can dominate the model's output.

The "gentle" middle ground between doing nothing and outright deleting features.

Why regularization is the preferred default Feature selection makes a hard, binary decision (keep or discard) about each feature, which risks losing real signal. Regularization instead makes a soft decision: every feature stays in the model, but features that don't help much get pushed toward having very little influence (small w_j), while features that genuinely matter can still have a meaningful weight. This is why the lecturer says he uses regularization "all the time," including later for neural networks.
Analogy Feature selection is like editing an essay by deleting entire paragraphs you think are unnecessary — effective, but risky if you guess wrong about what's unimportant. Regularization is like turning down the volume on every paragraph proportionally to how little it adds, without deleting any of them outright — safer, because even a "quiet" paragraph still contributes a little if it turns out to matter.

9. Cost Function With Regularization

The core trick: penalize large parameters directly in the cost

Suppose (illustrative example) you wanted w₃ and w₄ to end up close to 0 without deleting those features outright. You could simply add a huge penalty for them being large, directly into what gradient descent is trying to minimize:

Illustrative example — penalizing two specific parameters minimize: (1/2m) Σ (f(x⁽ⁱ⁾) − y⁽ⁱ⁾)²  +  1000·w₃²  +  1000·w₄²

Because 1000 is such a large multiplier, the only way to keep the whole expression small is for w₃ and w₄ to end up very close to 0 — effectively cancelling out those two polynomial terms without literally removing the features.

Generalizing: penalize every weight, a little

With many features (say 100), you usually don't know in advance which ones are the unimportant ones. So instead of singling out specific parameters, penalize all of them a bit:

Regularized cost function (general form) J(w,b) = [ original cost term ]  +  (λ / 2m) · Σj=1n wj²

The new second term is called the regularization term, and λ (lambda) is the regularization parameter — a number you choose, just like the learning rate α.

Why the (1/2m) scaling on the regularization term specifically

Why this matters Scaling both the original cost term and the regularization term by the same 1/2m (or 1/m) factor means that if your training set grows, the same λ value tends to keep working well. Without this scaling, a good λ for a small dataset might become far too strong or too weak once you collect more data — the scaling keeps the relative balance between "fit the data" and "keep weights small" stable across dataset sizes.

Why b is (conventionally) not regularized

By convention, the sum only runs over w₁ through w_n — the bias term b is left out. In practice it makes very little difference whether you regularize b too; some implementations do, most (including this course's convention) don't.

The two competing goals λ balances

TermWhat minimizing it encourages
Original cost term (MSE or log-loss)Fit the training data closely — accurate predictions
Regularization term (λ/2m)Σw_j²Keep the parameters small — a simpler, smoother model

What different values of λ actually do

λ = 0

Regularization term vanishes entirely. Model behaves exactly as before → free to overfit with a wiggly high-order curve.

λ huge (e.g. 10¹⁰)

Only way to minimize is forcing nearly every w_j to ≈ 0. Model collapses to roughly f(x) ≈ b — a flat line → underfits badly.

λ "just right"

Balances the two goals — keeps all the polynomial features but with modest weights, producing a smooth curve that still fits the data well.

λ is itself a hyperparameter you must choose Just as picking a bad learning rate α can break gradient descent, picking a bad λ breaks the fit in one of the two directions above. The course notes that later material covers systematic ways to select a good λ (model selection) — for now, treat picking it as trial-and-observe using held-out validation performance.

10. Regularized Linear Regression + Gradient Descent

Regularized cost function for linear regression J(w,b) = (1/2m) Σi=1m (f(x⁽ⁱ⁾) − y⁽ⁱ⁾)²  +  (λ/2m) Σj=1n wj²

The updated gradient descent rules

Only the w_j update changes; b's update is untouched wj = wj − α · [ (1/m) Σ (f(x⁽ⁱ⁾) − y⁽ⁱ⁾) xj⁽ⁱ⁾  +  (λ/m) wj ]
b = b − α · (1/m) Σ (f(x⁽ⁱ⁾) − y⁽ⁱ⁾)

The only change versus the unregularized version is the single extra term + (λ/m)·w_j tacked onto the end of the wj derivative. Because b isn't regularized, its update formula is identical to before.

The "shrink a little every step" intuition (optional-but-illuminating rearrangement)

Rearranging the wj update algebraically:

wj = wj · (1 − α·λ/m)  −  α · (1/m) Σ (f(x⁽ⁱ⁾) − y⁽ⁱ⁾) xj⁽ⁱ⁾

The second term is exactly the usual (unregularized) gradient descent update. The new first factor, (1 − α·λ/m), is a number just slightly less than 1 — for typical values like α=0.01, λ=1, m=50, this works out to 1 − 0.0002 = 0.9998.

Why this matters — this is the real mechanism of regularization Every single iteration of gradient descent, before even applying the usual update, you multiply w_j by a number slightly less than 1. That's a tiny proportional shrink applied every step, on top of the normal learning update. Repeated over thousands of iterations, this steady multiplicative shrinkage is what keeps the parameters small — it's not a one-time clamp, it's constant gentle pressure toward zero throughout training.
Analogy Think of unregularized gradient descent as a hiker walking downhill toward the cost minimum. Regularization adds a very light constant breeze blowing the hiker slightly back toward the "origin" (all weights = 0) on every single step — not strong enough to stop them reaching a good minimum, but enough to keep them from wandering to an extreme, wiggly, large-weight solution.

Where the extra term comes from (brief, optional calculus note)

Differentiating the added regularization term (λ/2m)w_j² with respect to w_j gives (λ/m)w_j — a standard power-rule derivative — which is exactly the new term appended to the gradient. The course explicitly marks this derivation as optional; you don't need to reproduce it, only to trust and use the resulting update rule.

11. Regularized Logistic Regression + Gradient Descent

Logistic regression is just as prone to overfitting as linear regression — especially with high-order polynomial features feeding into the sigmoid, which can produce an overly complex decision boundary (as shown in Section 6's third panel).

Regularized cost function for logistic regression J(w,b) = −(1/m) Σi=1m [ y⁽ⁱ⁾log(f(x⁽ⁱ⁾)) + (1−y⁽ⁱ⁾)log(1−f(x⁽ⁱ⁾)) ]  +  (λ/2m) Σj=1n wj²

This is exactly the log-loss cost function from the earlier lecture, with the identical regularization term from linear regression simply appended.

Gradient descent update — same shape as regularized linear regression wj = wj − α · [ (1/m) Σ (f(x⁽ⁱ⁾) − y⁽ⁱ⁾) xj⁽ⁱ⁾  +  (λ/m) wj ]
b = b − α · (1/m) Σ (f(x⁽ⁱ⁾) − y⁽ⁱ⁾)
The formula looks identical to regularized linear regression — the difference is hidden inside f(x) Exactly the same pattern as Section 2: the update-rule algebra is the same because both cost functions were engineered to produce this same clean derivative shape. But here, f(x) = g(w·x+b) is the sigmoid-based logistic function, not the plain linear function. Never let the matching formulas fool you into thinking these are the same model.

What regularization buys you here, concretely

Even when fitting a high-order polynomial decision boundary with many parameters, penalizing large w_j values steers the fitted boundary away from the overly-twisted shape in Section 6's third panel, back toward something closer to the smooth, "just right" ellipse — while still keeping every polynomial feature technically available to the model.

13. Summary & Key Takeaways

The full arc of this part

  1. Gradient descent for logistic regression uses the same-looking update rule as linear regression — w_j = w_j − α·(1/m)Σ(f(x⁽ⁱ⁾)−y⁽ⁱ⁾)x_j⁽ⁱ⁾ — but f(x) is the sigmoid-based logistic function, making it a genuinely different algorithm underneath.
  2. Lab 6 turns this into working code: compute_gradient_logistic (the math) plus gradient_descent (the loop), verified against expected output, then visualized as a shaded-probability plot with the 0.5-decision boundary drawn on top.
  3. Lab 7 shows the same task done in one line with sklearn.linear_model.LogisticRegression — .fit(), .predict(), .score().
  4. Overfitting (high variance) and underfitting (high bias) are the two failure modes on either side of a "just right" model — a training cost of exactly 0 is a warning sign, not a success.
  5. Three fixes: collect more data, select fewer features, or — most flexible — regularize, which shrinks all parameters without deleting any features.
  6. Regularization adds (λ/2m)Σw_j² to the cost function, which turns into one extra term, +(λ/m)w_j, in the gradient — equivalent to multiplying w_j by a number just under 1 on every single gradient descent step.
  7. λ = 0 → overfits (same as no regularization). λ → ∞ → underfits (all weights collapse toward 0). A well-chosen λ balances fitting the data against keeping weights small.
  8. Regularized logistic regression combines the log-loss cost with the exact same regularization term and produces an update rule with the same extra +(λ/m)w_j term — the bias b stays unregularized by convention in both linear and logistic cases.
  9. Lab 9 lets you see all of this live: dragging λ up from 0 visibly smooths an overfit curve or decision boundary, closing the loop between formula and behavior.
The one idea to hold onto above all others Every model you'll ever train faces the same tension: fit the training data well vs. stay simple enough to generalize. Gradient descent with a plain cost function only optimizes the first half. Regularization is the mechanism that keeps the second half in check — and it's the exact same idea (penalize large weights in the cost function) that reappears, largely unchanged, when you get to neural networks later in this specialization.
